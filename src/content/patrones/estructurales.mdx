Los patrones **estructurales** responden a una pregunta: ¿cómo combino objetos que ya existen para formar algo más grande sin que todo quede pegado con cinta? Casi todos se apoyan en la misma herramienta, la **composición**: un objeto guarda una referencia a otro y le delega trabajo. Lo que cambia entre ellos es la **intención**.

Eso los vuelve confusos al principio. Adapter, Decorator y Proxy tienen diagramas casi idénticos (una clase que envuelve a otra), y aun así resuelven problemas distintos. Por eso este tema termina cada patrón con "cuándo no usarlo" y "con qué se confunde", e incluye una sección dedicada a la pregunta de entrevista más común de la familia: **Decorator vs. Proxy vs. Adapter vs. Facade**.

El recorrido: primero los cuatro "envoltorios" (Adapter, Decorator, Facade, Proxy), después los que organizan estructuras (Composite y Bridge) y al final el que ahorra memoria (Flyweight).

## Adapter

**Intención:** convertir la interfaz de una clase en otra que el cliente espera, para que colaboren clases que de otro modo no podrían.

El caso de manual: tu dominio define cómo cobra (`PaymentGateway.charge(amount: Money, orderId)`), pero el proveedor que te toca integrar trae un SDK con otra forma: recibe centavos y moneda por separado, devuelve códigos numéricos en lugar de excepciones y llama "referencia" a lo que tú llamas pedido.

```ts title="checkout.ts (antes)"
// El SDK del proveedor se filtra por todo el código de negocio.
const res = legacyPay.makePayment(Math.round(order.total.amount * 100), order.total.currency, `ORD-${order.id}`)
if (res.code === 51) throw new InsufficientFunds()
if (res.code !== 0) throw new PaymentFailed(String(res.code))
order.markPaid(res.txn)
// ...y la misma traducción de códigos se repite en refunds.ts y subscriptions.ts
```

Si mañana cambias de proveedor, tocas cada archivo que conoce `makePayment` y sus códigos mágicos. El Adapter encierra esa traducción en **un solo objeto** que implementa tu interfaz y por dentro habla el idioma del SDK.

```ts title="TypeScript"
interface PaymentGateway {
  charge(amount: Money, orderId: string): Promise<{ transactionId: string }>
}

class LegacyPayAdapter implements PaymentGateway {
  constructor(private readonly client: LegacyPayClient) {}

  async charge(amount: Money, orderId: string) {
    const res = await this.client.makePayment(
      Math.round(amount.amount * 100), // el SDK quiere centavos
      amount.currency,
      `ORD-${orderId}`,
    )
    switch (res.code) {
      case 0: return { transactionId: res.txn }
      case 51: throw new InsufficientFunds()
      case 54: throw new CardExpired()
      default: throw new PaymentFailed(`LegacyPay code ${res.code}`)
    }
  }
}

// El checkout no sabe que existe LegacyPay:
const checkout = new CheckoutService(new LegacyPayAdapter(new LegacyPayClient(apiKey)))
```

```python title="Python"
from typing import Protocol

class PaymentGateway(Protocol):
    def charge(self, amount: "Money", order_id: str) -> str: ...

ERRORS = {51: InsufficientFunds, 54: CardExpired}

class LegacyPayAdapter:
    def __init__(self, client: "LegacyPayClient") -> None:
        self._client = client

    def charge(self, amount: "Money", order_id: str) -> str:
        res = self._client.make_payment(
            round(amount.amount * 100), amount.currency, f"ORD-{order_id}"
        )
        if res.code == 0:
            return res.txn
        raise ERRORS.get(res.code, PaymentFailed)(f"LegacyPay code {res.code}")

checkout = CheckoutService(LegacyPayAdapter(LegacyPayClient(api_key)))
```

GoF describe dos variantes. El **adapter de objetos** (el de arriba) usa composición y es el que usarás casi siempre. El **adapter de clases** hereda del adaptado e implementa la interfaz objetivo; necesita herencia múltiple o que el adaptado sea una clase extensible, y acopla más.

**Dónde aparece:** `InputStreamReader` en Java adapta un flujo de bytes a un `Reader` de caracteres, y `Arrays.asList` presenta un arreglo como `List`. Axios elige un *adapter* distinto según el entorno (XHR en el navegador, el módulo `http` en Node) detrás de la misma API. A escala de arquitectura, los "adaptadores" de la [arquitectura hexagonal](/arquitectura/hexagonal) y la *anti-corruption layer* de [DDD estratégico](/arquitectura/ddd-estrategico) son este mismo patrón aplicado a un sistema completo.

**Cuándo no usarlo:** si controlas ambos lados, cambia la interfaz en lugar de agregar una capa de traducción. Y si el adapter empieza a tener lógica de negocio (descuentos, reglas de reintento), ya no es un adapter: esa lógica pertenece a tu dominio.

**Relacionados:** Facade también envuelve, pero simplifica un subsistema entero en vez de traducir un objeto. Bridge separa abstracción e implementación **de antemano**; Adapter arregla una incompatibilidad **después**.

## Decorator

**Intención:** agregar responsabilidades a un objeto de forma dinámica, envolviéndolo en otro que implementa la misma interfaz.

Imagina el cliente HTTP con el que tu servicio de pedidos llama a la API de inventario. Primero necesitas logs. Después, reintentos ante errores 503. Después, caché para las lecturas. Después, un token de autenticación. Hay dos caminos malos:

- **Subclases por combinación:** `LoggingHttpClient`, `RetryingHttpClient`, `LoggingRetryingHttpClient`, `CachedLoggingRetryingHttpClient`... Con 4 comportamientos opcionales hay 2⁴ = 16 combinaciones posibles.
- **Flags dentro de una clase:** `if (this.opts.retry) ... if (this.opts.cache) ...`. La clase crece con cada requisito nuevo y cada `if` se cruza con los demás.

Decorator propone otra cosa: cada comportamiento es un objeto pequeño que **implementa `HttpClient` y envuelve otro `HttpClient`**. Haces su trabajo antes o después de delegar. Como todos comparten interfaz, se apilan como capas de cebolla, y el código que usa el cliente no sabe cuántas capas hay.

<DecoratorStack />

Juega con el orden. Tres lecciones que el widget hace visibles:

1. **Logging por fuera de Retry** registra una llamada lógica; **por dentro**, registra cada intento. Ninguna es incorrecta: depende de qué quieres medir.
2. **Caché por fuera de Retry** evita reintentar cuando hay un *hit*. Al revés, cada reintento vuelve a consultar la caché, lo que es redundante.
3. **Caché por fuera de Auth** es un riesgo real: la caché responde antes de saber quién pregunta, y en un cliente compartido podrías servir la respuesta de un usuario a otro.

```ts title="TypeScript"
interface HttpClient {
  get(url: string): Promise<Response>
}

class FetchHttpClient implements HttpClient {
  get(url: string) { return fetch(url) }
}

class RetryClient implements HttpClient {
  constructor(private readonly inner: HttpClient, private readonly attempts = 3) {}

  async get(url: string) {
    for (let i = 1; ; i++) {
      const res = await this.inner.get(url)
      if (res.status < 500 || i === this.attempts) return res
      await sleep(100 * 2 ** (i - 1)) // backoff exponencial
    }
  }
}

class CachingClient implements HttpClient {
  private cache = new Map<string, { body: string; expires: number }>()
  constructor(private readonly inner: HttpClient, private readonly ttlMs = 30_000) {}

  async get(url: string) {
    const hit = this.cache.get(url)
    if (hit && hit.expires > Date.now()) return new Response(hit.body)
    const res = await this.inner.get(url)
    if (res.ok) this.cache.set(url, { body: await res.clone().text(), expires: Date.now() + this.ttlMs })
    return res
  }
}

// La composición se lee de afuera hacia adentro:
const inventory: HttpClient = new CachingClient(new RetryClient(new FetchHttpClient()))
```

```python title="Python"
import functools, time
from typing import Protocol

class HttpClient(Protocol):
    def get(self, url: str) -> "Response": ...

class RetryClient:
    def __init__(self, inner: HttpClient, attempts: int = 3) -> None:
        self._inner, self._attempts = inner, attempts

    def get(self, url: str) -> "Response":
        for i in range(1, self._attempts + 1):
            res = self._inner.get(url)
            if res.status_code < 500 or i == self._attempts:
                return res
            time.sleep(0.1 * 2 ** (i - 1))

class CachingClient:
    def __init__(self, inner: HttpClient) -> None:
        self._inner, self._cache = inner, {}

    def get(self, url: str) -> "Response":
        if url not in self._cache:
            self._cache[url] = self._inner.get(url)
        return self._cache[url]

client = CachingClient(RetryClient(RequestsClient()))

# El mismo patrón a nivel de función: los decoradores de Python.
@functools.lru_cache(maxsize=1024)
def exchange_rate(currency: str) -> float:
    return fetch_rate(currency)
```

<Callout type="note" title="Tres cosas que se llaman 'decorator'">

El patrón GoF (envolver un objeto con la misma interfaz), los **decoradores de Python** (`@functools.lru_cache` envuelve una función: es el mismo patrón aplicado a funciones) y los **decoradores de TypeScript/Java** (`@Injectable()`, `@Transactional`), que son anotaciones de metaprogramación. Estos últimos a veces *se implementan* con un proxy o un decorador por debajo, pero el término no significa lo mismo.

</Callout>

**Dónde aparece:** la biblioteca de I/O de Java es el ejemplo canónico. `new BufferedInputStream(new FileInputStream("pedidos.csv"))` agrega un búfer a un flujo, y `GZIPInputStream` agrega descompresión; todos son `InputStream`. En el ecosistema web, los *interceptors* de NestJS y Axios cumplen la misma función de envolver llamadas. Los middleware de Express se parecen, pero allí cada eslabón puede **cortar** la cadena, lo que los acerca más a [Chain of Responsibility](/patrones/comportamiento-2).

**Cuándo no usarlo:** si la capa extra **siempre** está presente y nunca cambia, puede vivir dentro de la clase. Las pilas profundas complican la depuración (trazas largas, ¿en qué capa se perdió el header?) y rompen las comparaciones de identidad: un `CachingClient` no es `instanceof FetchHttpClient`. Y como viste, **el orden importa**, lo que convierte el armado de la pila en una decisión de diseño que hay que documentar.

**Relacionados:** Proxy tiene la misma estructura con otra intención. Strategy y Decorator se complementan; Refactoring.Guru lo resume así: Decorator te deja cambiar la piel de un objeto, Strategy te deja cambiar sus entrañas. Un Decorator es como un Composite con un solo hijo.

## Facade

**Intención:** ofrecer una interfaz unificada y simple a un conjunto de interfaces de un subsistema.

Confirmar un pedido toca seis piezas: reservar stock, calcular precio, calcular impuestos, cobrar, generar la etiqueta de envío y mandar el correo. Si cada controlador (web, app móvil, job de reintentos) orquesta esas seis llamadas por su cuenta, el orden y el manejo de errores se duplican en tres lugares y divergen con el tiempo.

```ts title="orders-controller.ts (antes)"
await inventory.reserve(cart.items)
const price = pricing.calculate(cart, customer.tier)
const tax = taxes.compute(price, customer.address)
const payment = await payments.charge(price.add(tax), customer.paymentMethod)
const label = await shipping.createLabel(customer.address, cart.weight())
await mailer.send(customer.email, 'order-confirmed', { label })
// ¿Y si el cobro falla? ¿Quién libera el stock reservado?
```

La Facade le pone un nombre a esa secuencia y la esconde detrás de una operación de alto nivel:

```ts title="TypeScript"
export class CheckoutFacade {
  constructor(
    private readonly inventory: Inventory,
    private readonly pricing: Pricing,
    private readonly payments: Payments,
    private readonly shipping: Shipping,
    private readonly mailer: Mailer,
  ) {}

  async placeOrder(cart: Cart, customer: Customer): Promise<OrderConfirmation> {
    const reservation = await this.inventory.reserve(cart.items)
    try {
      const total = this.pricing.totalWithTax(cart, customer)
      const payment = await this.payments.charge(total, customer.paymentMethod)
      const label = await this.shipping.createLabel(customer.address, cart.weight())
      await this.mailer.send(customer.email, 'order-confirmed', { label })
      return { paymentId: payment.id, trackingCode: label.tracking }
    } catch (err) {
      await this.inventory.release(reservation) // la política de compensación vive en un lugar
      throw err
    }
  }
}
```

```python title="Python"
class CheckoutFacade:
    def __init__(self, inventory, pricing, payments, shipping, mailer) -> None:
        self._inventory = inventory
        self._pricing = pricing
        self._payments = payments
        self._shipping = shipping
        self._mailer = mailer

    def place_order(self, cart: "Cart", customer: "Customer") -> "OrderConfirmation":
        reservation = self._inventory.reserve(cart.items)
        try:
            total = self._pricing.total_with_tax(cart, customer)
            payment = self._payments.charge(total, customer.payment_method)
            label = self._shipping.create_label(customer.address, cart.weight())
            self._mailer.send(customer.email, "order-confirmed", label=label)
            return OrderConfirmation(payment.id, label.tracking)
        except Exception:
            self._inventory.release(reservation)
            raise
```

**Dónde aparece:** jQuery fue, en esencia, una gran facade sobre las APIs del DOM de cada navegador. La clase `Upload` de `@aws-sdk/lib-storage` esconde la subida multiparte a S3 (iniciar, partir, subir en paralelo, completar o abortar) detrás de un solo `upload.done()`. `requests` en Python ofrece una cara amable sobre `urllib3`. Y en una arquitectura por capas, los *application services* suelen ser facades sobre el dominio (lo verás en [monolito y capas](/arquitectura/monolito-y-capas)).

**Cuándo no usarlo:** una facade no debe convertirse en el único camino ni en un objeto que sabe de todo. Si empieza a acumular reglas de negocio de cinco dominios, se está volviendo un *god object* ([antipatrones](/patrones/antipatrones)). Y no prohíbas el acceso directo al subsistema: la facade simplifica el caso común, no reemplaza las piezas.

**Relacionados:** Adapter cambia una interfaz; Facade **define una nueva y más simple**. [Mediator](/patrones/comportamiento-2) también centraliza, pero allí los colegas conocen al mediador y se comunican a través de él; en Facade la relación es de un solo sentido. En el mundo distribuido, un API gateway o un *backend for frontend* cumplen un rol de facade entre servicios ([APIs](/system-design/apis)).

## Proxy

**Intención:** ofrecer un sustituto de otro objeto para controlar el acceso a él.

El Proxy implementa la misma interfaz que el objeto real, así que el cliente no nota la diferencia. Lo que hace por dentro define su variante:

- **Virtual:** retrasa la creación de un objeto caro hasta que de verdad se necesita (carga perezosa).
- **De protección:** verifica permisos antes de delegar.
- **Remoto:** representa localmente un objeto que vive en otro proceso o máquina (los *stubs* de gRPC o RMI).
- **De caché:** guarda resultados para no repetir operaciones costosas.
- **Smart reference:** cuenta referencias, registra accesos o libera recursos cuando nadie usa el objeto.

El widget compara un visor de planos sin proxy (descarga todo al abrir) con un proxy virtual y con un proxy que además comparte caché entre aperturas del documento:

```ts title="TypeScript"
interface Image {
  display(): Promise<Bitmap>
}

class RemoteImage implements Image {
  private constructor(private readonly bitmap: Bitmap) {}
  static async load(url: string) { return new RemoteImage(await download(url)) } // caro
  async display() { return this.bitmap }
}

// Proxy virtual: misma interfaz, creación diferida.
class LazyImageProxy implements Image {
  private real?: Promise<RemoteImage>
  constructor(private readonly url: string) {}

  display() {
    this.real ??= RemoteImage.load(this.url) // solo la primera vez
    return this.real.then((img) => img.display())
  }
}

// Proxy de protección: misma interfaz, control de acceso.
class ConfidentialPlanProxy implements Image {
  constructor(private readonly inner: Image, private readonly user: User) {}
  display() {
    if (!this.user.can('plans:read-confidential')) throw new Forbidden()
    return this.inner.display()
  }
}

const pages: Image[] = urls.map((u) => new LazyImageProxy(u)) // nada se descarga aún
```

```python title="Python"
class RemoteImage:
    def __init__(self, url: str) -> None:
        self._bitmap = download(url)  # caro

    def display(self) -> "Bitmap":
        return self._bitmap

class LazyImageProxy:
    """Proxy virtual: misma interfaz que RemoteImage, carga diferida."""

    def __init__(self, url: str) -> None:
        self._url = url
        self._real: RemoteImage | None = None

    def display(self) -> "Bitmap":
        if self._real is None:
            self._real = RemoteImage(self._url)
        return self._real.display()

# Proxy genérico con __getattr__: delega todo lo que no redefine.
class LoggingProxy:
    def __init__(self, target: object) -> None:
        self._target = target

    def __getattr__(self, name: str):
        attr = getattr(self._target, name)
        logger.debug("acceso a %s.%s", type(self._target).__name__, name)
        return attr
```

**Dónde aparece:** en todos lados, a menudo sin que lo veas.

- **ORMs:** Hibernate/JPA devuelven proxies para asociaciones perezosas; tocar `order.getCustomer().getName()` dispara la consulta. De ahí viene el famoso problema N+1.
- **Spring:** `@Transactional` funciona porque Spring envuelve tu bean en un proxy (JDK dynamic proxy o una subclase generada con CGLIB). Consecuencia clásica de entrevista: si un método de la clase llama a otro método `@Transactional` **de la misma clase** con `this`, la llamada no pasa por el proxy y la transacción no se aplica.
- **JavaScript:** el objeto nativo `Proxy` intercepta lecturas y escrituras. Vue 3 construye su sistema de reactividad sobre él.
- **Red:** un *reverse proxy* como Nginx es la misma idea a nivel de infraestructura: mismo "contrato" HTTP, con control de acceso, caché y balanceo en el medio.

**Cuándo no usarlo:** cada proxy agrega indirección y puede esconder costos. Un proxy remoto que parece un objeto local invita a hacer cien llamadas pequeñas por la red como si fueran gratis, y la red no es gratis ni confiable ([confiabilidad](/system-design/confiabilidad)). La carga perezosa también mueve la latencia a un momento inesperado (el primer clic) y puede producir errores fuera de la transacción donde los esperabas.

**Relacionados:** Decorator (misma forma, otra intención), Adapter (cambia la interfaz; el proxy la conserva) y la caché como estrategia de sistema ([caching](/system-design/caching)).

## Decorator vs. Proxy vs. Adapter vs. Facade

Los cuatro son envoltorios, y en un diagrama de clases pueden verse idénticos. La forma de distinguirlos es preguntarte **qué interfaz expone el envoltorio** y **para qué existe**.

<Compare>
<Option title="Adapter" verdict="Otra interfaz → la que esperas">

Envuelve **un** objeto con una interfaz **incompatible** y la traduce a la que el cliente espera. Se agrega después, cuando dos piezas ya existen y no encajan. No agrega comportamiento: traduce.

</Option>
<Option title="Decorator" verdict="Misma interfaz + comportamiento">

Expone **la misma** interfaz y **agrega** responsabilidades (logs, reintentos, caché). Está pensado para **apilarse**, y normalmente es el cliente (o la composition root) quien arma la pila.

</Option>
<Option title="Proxy" verdict="Misma interfaz + control de acceso">

Expone **la misma** interfaz y **controla el acceso** al objeto real: cuándo se crea, quién puede usarlo, dónde vive. A menudo el proxy **gestiona el ciclo de vida** del sujeto, y el cliente ni sabe que existe.

</Option>
<Option title="Facade" verdict="Interfaz nueva y más simple">

Expone una interfaz **nueva** sobre **varios** objetos de un subsistema. No traduce uno a uno: resume una secuencia de pasos en una operación de alto nivel.

</Option>
</Compare>

La línea entre Decorator y Proxy es la más difusa. Una caché puede verse como decorador (agrega comportamiento) o como proxy (controla el acceso al objeto caro). El propio libro GoF admite que un proxy de protección puede implementarse exactamente como un decorador: la diferencia es el propósito. Refactoring.Guru agrega una pista práctica: la composición de decoradores la controla el cliente, mientras que el proxy suele gestionar por su cuenta el ciclo de vida del objeto real. En una entrevista, lo que se evalúa no es que elijas la etiqueta "correcta", sino que expliques la **intención** y el **trade-off**.

<Callout type="interview" title="Cómo responder en 30 segundos">

"Adapter cambia la interfaz para que algo encaje. Decorator mantiene la interfaz y agrega comportamiento apilable. Proxy mantiene la interfaz y controla el acceso: carga perezosa, permisos u objetos remotos. Facade crea una interfaz nueva y simple sobre un subsistema completo." Si quieres un ejemplo para cada uno: `InputStreamReader`, `BufferedInputStream`, el proxy de `@Transactional` en Spring y la clase `Upload` del SDK de AWS.

</Callout>

## Composite

**Intención:** componer objetos en estructuras de árbol y permitir que el cliente trate igual a los objetos individuales y a las composiciones.

Un envío tiene productos, pero también cajas que contienen productos y otras cajas. Si el código que calcula el costo de envío tiene que preguntar "¿esto es una caja o un producto?" en cada nivel, la recursión queda desparramada por el cliente:

```ts title="shipping-cost.ts (antes)"
function totalWeight(item: Product | Box): number {
  if (item instanceof Box) {
    let sum = item.packagingWeight
    for (const child of item.contents) sum += totalWeight(child)
    return sum
  }
  return item.weight
}
// ...y la misma forma se repite en totalPrice, countItems, hasHazardousGoods...
```

Composite define una interfaz común (`ShipmentItem`) que implementan tanto las hojas (`Product`) como los compuestos (`Box`). Cada caja resuelve su total **delegando en sus hijos**, sin saber si son productos o más cajas. El cliente llama `weight()` en la raíz y listo.

<CompositeTree />

Recorre el árbol paso a paso: la pila de llamadas crece al entrar a cada caja y se resuelve de abajo hacia arriba. Contraer una caja no cambia su total, porque el cálculo no depende de lo que el cliente ve, sino de la estructura.

```ts title="TypeScript"
interface ShipmentItem {
  price(): number
  weight(): number
}

class Product implements ShipmentItem {
  constructor(readonly name: string, private readonly _price: number, private readonly _weight: number) {}
  price() { return this._price }
  weight() { return this._weight }
}

class Box implements ShipmentItem {
  private readonly children: ShipmentItem[] = []
  constructor(readonly label: string, private readonly packaging = { price: 1.5, weight: 0.3 }) {}

  add(...items: ShipmentItem[]) { this.children.push(...items); return this }
  price() { return this.children.reduce((s, c) => s + c.price(), this.packaging.price) }
  weight() { return this.children.reduce((s, c) => s + c.weight(), this.packaging.weight) }
}

const shipment = new Box('Caja grande').add(
  new Product('Laptop', 1200, 2.1),
  new Box('Caja mediana').add(new Product('Mouse', 25, 0.1), new Product('Cable USB-C', 12, 0.05)),
)
shipment.weight() // el cliente no sabe cuántos niveles hay
```

```python title="Python"
from dataclasses import dataclass, field
from typing import Protocol

class ShipmentItem(Protocol):
    def price(self) -> float: ...
    def weight(self) -> float: ...

@dataclass(frozen=True)
class Product:
    name: str
    _price: float
    _weight: float
    def price(self) -> float: return self._price
    def weight(self) -> float: return self._weight

@dataclass
class Box:
    label: str
    packaging_price: float = 1.5
    packaging_weight: float = 0.3
    children: list[ShipmentItem] = field(default_factory=list)

    def add(self, *items: ShipmentItem) -> "Box":
        self.children.extend(items)
        return self

    def price(self) -> float:
        return self.packaging_price + sum(c.price() for c in self.children)

    def weight(self) -> float:
        return self.packaging_weight + sum(c.weight() for c in self.children)
```

</CodeTabs>

<Details summary="Profundizar: transparencia vs. seguridad">

¿Dónde declaras `add(child)`? Si lo pones en la interfaz común (*transparencia*), el cliente trata todo igual, pero `product.add(...)` compila y tiene que fallar en runtime. Si lo dejas solo en `Box` (*seguridad*), el compilador te protege, pero a veces el cliente tiene que preguntar el tipo para agregar hijos. GoF discute ambos lados y se inclina por la transparencia; los lenguajes con tipos estáticos modernos suelen preferir la seguridad (como el ejemplo de arriba). No hay una respuesta universal: elige según quién arma el árbol y quién lo recorre.

</Details>

**Dónde aparece:** el DOM y el árbol de componentes de React (un componente renderiza elementos o más componentes), los sistemas de archivos (carpetas y archivos con `size()`), los widgets de Flutter, los árboles sintácticos de un compilador, los grupos de permisos que contienen usuarios u otros grupos, y la lista de materiales (BOM) en manufactura.

**Cuándo no usarlo:** si la jerarquía no es recursiva (pedido → líneas, y punto), un array basta. Si las hojas y los compuestos necesitan operaciones muy distintas, forzar una interfaz común produce métodos vacíos o que lanzan excepciones. Con árboles muy grandes, recalcular totales en cada llamada puede ser caro: cachea o mantén agregados actualizados.

**Relacionados:** [Iterator](/patrones/comportamiento-2) para recorrer el árbol, [Visitor](/patrones/comportamiento-2) para agregar operaciones nuevas sin tocar las clases, Builder para armar árboles complejos y Decorator, que es un "composite de un solo hijo".

## Bridge

**Intención:** desacoplar una abstracción de su implementación para que ambas puedan variar de forma independiente.

Bridge resuelve una explosión combinatoria en **dos dimensiones**. Tu sistema envía tres tipos de notificación (alerta de pedido, recordatorio de carrito, promoción) por tres canales (email, SMS, push). Si modelas cada combinación con herencia, terminas con nueve clases (`EmailOrderAlert`, `SmsOrderAlert`, `PushOrderAlert`, `EmailReminder`...) y agregar WhatsApp suma tres más.

Bridge parte la jerarquía en dos: la **abstracción** (qué notificas y con qué reglas) y la **implementación** (por dónde viaja). La abstracción guarda una referencia a la implementación: ese "puente" es una simple composición. Ahora tienes 3 + 3 clases, y cada dimensión crece por separado.

```ts title="TypeScript"
// Implementador: operaciones primitivas de un canal.
interface Channel {
  deliver(to: User, title: string, body: string): Promise<void>
}

class EmailChannel implements Channel {
  deliver(to: User, title: string, body: string) { return smtp.send(to.email, title, body) }
}
class SmsChannel implements Channel {
  deliver(to: User, _title: string, body: string) { return twilio.send(to.phone, body.slice(0, 160)) }
}

// Abstracción: reglas de negocio de cada tipo de notificación.
abstract class Notification {
  constructor(protected readonly channel: Channel) {}
  abstract send(user: User): Promise<void>
}

class OrderAlert extends Notification {
  constructor(channel: Channel, private readonly order: Order) { super(channel) }
  send(user: User) {
    return this.channel.deliver(user, `Pedido ${this.order.id}`, `Tu pedido está ${this.order.status}`)
  }
}

class Promotion extends Notification {
  constructor(channel: Channel, private readonly campaign: Campaign) { super(channel) }
  async send(user: User) {
    if (!user.marketingOptIn || isQuietHours(user.timezone)) return
    await this.channel.deliver(user, this.campaign.title, this.campaign.body)
  }
}

// Cualquier combinación, sin clases nuevas:
await new Promotion(new SmsChannel(), blackFriday).send(user)
```

```python title="Python"
from abc import ABC, abstractmethod
from typing import Protocol

class Channel(Protocol):
    def deliver(self, to: "User", title: str, body: str) -> None: ...

class Notification(ABC):
    def __init__(self, channel: Channel) -> None:
        self._channel = channel  # el "puente"

    @abstractmethod
    def send(self, user: "User") -> None: ...

class OrderAlert(Notification):
    def __init__(self, channel: Channel, order: "Order") -> None:
        super().__init__(channel)
        self._order = order

    def send(self, user: "User") -> None:
        self._channel.deliver(user, f"Pedido {self._order.id}", f"Tu pedido está {self._order.status}")

class Promotion(Notification):
    def __init__(self, channel: Channel, campaign: "Campaign") -> None:
        super().__init__(channel)
        self._campaign = campaign

    def send(self, user: "User") -> None:
        if user.marketing_opt_in and not is_quiet_hours(user.timezone):
            self._channel.deliver(user, self._campaign.title, self._campaign.body)

Promotion(SmsChannel(), black_friday).send(user)
```

</CodeTabs>

**Dónde aparece:** JDBC se cita a menudo como Bridge: tu código usa la API de `java.sql` (la abstracción) y cada driver de base de datos aporta la implementación. SLF4J separa la API de logging del backend (Logback, Log4j) con la misma lógica. En gráficos, las formas (círculo, rectángulo) suelen desacoplarse del motor que las dibuja (SVG, Canvas, OpenGL).

**Cuándo no usarlo:** si solo hay **una** dimensión de variación, Bridge es una indirección sin beneficio. Tampoco lo diseñes "por si acaso": nace de detectar dos ejes reales de cambio. Si ya tienes dos interfaces incompatibles, lo que necesitas es un Adapter.

**Relacionados:** estructuralmente se parece a [Strategy](/patrones/comportamiento-1) (un objeto delega en otro intercambiable). La diferencia es la intención: Bridge organiza una jerarquía completa en dos ejes de forma estable; Strategy intercambia un algoritmo, a menudo en runtime. Abstract Factory puede crear la implementación correcta para cada plataforma.

## Flyweight

**Intención:** compartir eficientemente una gran cantidad de objetos pequeños separando el estado **intrínseco** (compartible e inmutable) del **extrínseco** (propio de cada uso).

Imagina el mapa de seguimiento de una empresa de envíos que dibuja todos los paquetes activos de una ciudad. Supongamos 100.000 marcadores, cada uno con su ícono de 20 KB, su color y su tamaño según el estado del paquete. Si cada marcador guarda su propia copia del ícono, son unos 2 GB solo en imágenes. Pero solo hay cinco estados posibles (en bodega, en ruta, demorado, entregado, devuelto): **cinco íconos distintos**.

Flyweight separa lo que se repite de lo que no. El ícono, el color y el tamaño (estado intrínseco) viven en cinco objetos compartidos. La latitud, la longitud y el id del paquete (estado extrínseco) quedan en cada marcador o se pasan como parámetros. Una fábrica con caché garantiza que nunca se cree un segundo objeto para el mismo estado.

```ts title="TypeScript"
type Status = 'warehouse' | 'in_transit' | 'delayed' | 'delivered' | 'returned'

// Flyweight: inmutable y compartido.
class MarkerStyle {
  constructor(readonly icon: ImageBitmap, readonly color: string, readonly size: number) {
    Object.freeze(this)
  }
  draw(ctx: CanvasRenderingContext2D, x: number, y: number) {
    ctx.drawImage(this.icon, x - this.size / 2, y - this.size, this.size, this.size)
  }
}

class MarkerStyleFactory {
  private cache = new Map<Status, MarkerStyle>()
  get(status: Status): MarkerStyle {
    let style = this.cache.get(status)
    if (!style) {
      style = new MarkerStyle(loadIcon(status), colorFor(status), 28)
      this.cache.set(status, style)
    }
    return style
  }
}

// Cada marcador es liviano: coordenadas + referencia al estilo compartido.
const styles = new MarkerStyleFactory()
const markers = packages.map((p) => ({ lat: p.lat, lng: p.lng, id: p.id, style: styles.get(p.status) }))
// 100.000 marcadores, 5 instancias de MarkerStyle.
```

```python title="Python"
from dataclasses import dataclass
from functools import cache

@dataclass(frozen=True, slots=True)
class MarkerStyle:          # intrínseco: inmutable y compartido
    icon: bytes
    color: str
    size: int

@cache                      # la "fábrica" con caché: un estilo por estado
def marker_style(status: str) -> MarkerStyle:
    return MarkerStyle(load_icon(status), color_for(status), 28)

@dataclass(slots=True)      # extrínseco: slots reduce la memoria por instancia
class Marker:
    lat: float
    lng: float
    package_id: str
    style: MarkerStyle

markers = [Marker(p.lat, p.lng, p.id, marker_style(p.status)) for p in packages]
```

</CodeTabs>

**Dónde aparece:** `Integer.valueOf(int)` en Java reutiliza instancias para los valores entre -128 y 127 (por eso `==` entre `Integer` "funciona" con números chicos y falla con grandes, una pregunta trampa clásica). El *string pool* de Java y `sys.intern` en Python comparten cadenas idénticas. Los editores de texto y los motores de fuentes comparten los glifos, que es el ejemplo original del libro GoF. Los motores de videojuegos aplican la misma idea con *instancing*: una malla, miles de árboles en posiciones distintas.

**Cuándo no usarlo:** solo cuando hay **muchos** objetos y la memoria es un problema **medido**. Complica el código (el estado queda partido en dos lugares) y exige que lo compartido sea estrictamente inmutable: si alguien cambia el color de un `MarkerStyle`, cambian 20.000 marcadores a la vez. Con pocos miles de objetos, casi nunca compensa.

**Relacionados:** se combina con Composite (las hojas compartidas de un árbol), usa una fábrica con caché (un pariente de Factory Method) y conceptualmente es un caso particular de [caching](/system-design/caching) a nivel de objetos.

<Takeaways>

- Casi todos los patrones estructurales se basan en **composición y delegación**; lo que los distingue es la intención, no el diagrama.
- **Adapter** traduce una interfaz incompatible a la que esperas; **Facade** crea una interfaz nueva y simple sobre un subsistema completo.
- **Decorator** y **Proxy** conservan la interfaz: el primero agrega comportamiento apilable (y **el orden de las capas importa**), el segundo controla el acceso (carga perezosa, permisos, objetos remotos).
- **Composite** permite tratar hojas y grupos de forma uniforme; la recursión vive en los compuestos, no en el cliente.
- **Bridge** evita la explosión combinatoria cuando hay **dos** ejes de variación independientes; con uno solo es indirección innecesaria.
- **Flyweight** separa estado intrínseco (compartido e inmutable) de extrínseco; úsalo solo cuando la memoria sea un problema medido.
- En frameworks reales verás estos patrones sin su nombre: los streams de Java, los proxies de Spring y Hibernate, el `Proxy` de JavaScript, React y el DOM.

</Takeaways>
