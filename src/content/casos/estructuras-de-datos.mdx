## El arreglo dinámico

Un arreglo guarda sus elementos **contiguos en memoria**. Por eso el acceso por índice es O(1): la dirección del elemento `i` es `inicio + i × tamaño_del_elemento`, una multiplicación y una suma, sin recorrer nada.

El problema es que un bloque contiguo no puede crecer en el lugar: lo que está justo después en memoria puede estar ocupado. Un **arreglo dinámico** (la `list` de Python, el `ArrayList` de Java, el `Array` de JavaScript, el `std::vector` de C++, los slices de Go) resuelve esto reservando más espacio del que usa. Cuando se llena, pide un bloque más grande, **copia todo** y libera el viejo.

¿Entonces `append` es O(n)? A veces sí: el append que encuentra el arreglo lleno copia n elementos. Pero si la capacidad crece **en proporción** (por ejemplo, se duplica), esas copias caras son cada vez más raras. Con capacidades 1, 2, 4, 8… hasta n, el total de copias es 1 + 2 + 4 + … + n/2, que es menor que n. Repartido entre los n appends, cada uno paga como mucho 1 por escribir más 2 por las copias: **O(1) amortizado**.

Una forma de explicarlo que funciona bien en voz alta: cada append "paga" tres monedas. Una se gasta en escribirse. Las otras dos se ahorran: una para copiarse a sí mismo en el próximo crecimiento y otra para copiar a un elemento viejo que ya gastó sus ahorros. Cuando llega el crecimiento, la caja alcanza justo.

Mira qué pasa con distintas políticas de crecimiento. Con **+4 fijo**, el promedio no se estabiliza: sube con cada crecimiento, porque las copias suman 4 + 8 + 12 + …, que es cuadrático.

<DynamicArrayGrowth />

Detalles que suman en una entrevista:

- **Amortizado no es promedio.** "Promedio" habla de entradas aleatorias; "amortizado" garantiza el costo total de **cualquier** secuencia de operaciones. Un append puntual puede tardar O(n), y eso importa en sistemas sensibles a la latencia: si tu bucle de juego o tu servicio de baja latencia no tolera un pico, reserva la capacidad por adelantado (`reserve` en C++, `new ArrayList<>(n)` en Java, `make([]T, 0, n)` en Go).
- **El factor real varía.** Java `ArrayList` crece 1,5 veces; CPython sobreasigna alrededor de un 12,5 % más una constante. Cualquier factor mayor que 1 da O(1) amortizado; factores más chicos desperdician menos memoria y copian más seguido.
- **Insertar o borrar en el medio es O(n)**, porque hay que desplazar todo lo que sigue. `list.add(0, x)` en un `ArrayList` y `list.insert(0, x)` en Python son O(n); si necesitas insertar por los dos extremos, usa una deque (`ArrayDeque` en Java, `collections.deque` en Python).

### `ArrayList` en Java

Java es el lenguaje por defecto de estos apuntes, así que conviene saber cómo lo hace `ArrayList` en concreto (todo esto está en el código fuente de OpenJDK):

- `new ArrayList<>()` no reserva nada: el arreglo interno arranca vacío y el primer `add` reserva **10** lugares.
- Cuando se llena, la nueva capacidad es `vieja + (vieja >> 1)`, es decir **×1,5**: 10, 15, 22, 33, 49, 73… Cada crecimiento es un `Arrays.copyOf` de todo el contenido.
- Si sabes cuántos elementos vienen, `new ArrayList<>(n)` o `ensureCapacity(n)` evitan todas esas copias, y `trimToSize()` devuelve la memoria sobrante.
- Un `ArrayList<Integer>` no guarda los números contiguos: guarda **referencias** a objetos `Integer`, cada uno en otro lugar del heap. Para millones de números, un `int[]` ocupa varias veces menos memoria y se recorre mucho más rápido.

```java title="Java"
List<Integer> ids = new ArrayList<>(List.of(10, 20, 30, 40, 50));
ids.remove(1); // quita el índice 1 (el 20), no el valor 1
ids.remove(Integer.valueOf(40)); // quita el valor 40: queda [10, 30, 50]
// for (Integer id : ids) if (id == 10) ids.remove(id); // ConcurrentModificationException
ids.removeIf(id -> id == 10); // así sí: queda [30, 50]
```

<Callout type="tip" title="En Java">

En una `List<Integer>`, `remove(1)` borra **la posición** 1, no el valor 1: el `int` elige la sobrecarga `remove(int index)`. Para borrar el valor, `remove(Integer.valueOf(1))`. Y no borres dentro de un for-each: el iterador detecta el cambio y lanza `ConcurrentModificationException` (usa `removeIf` o `iterator.remove()`).

</Callout>

## La lista enlazada (y por qué rara vez gana)

Una lista enlazada guarda cada elemento en un nodo separado, con un puntero al siguiente (y al anterior, si es doblemente enlazada). La teoría dice que gana en inserción y borrado: O(1) contra O(n) del arreglo. La práctica es más matizada, por dos razones.

**Primera: el O(1) es "si ya tienes el nodo".** Para insertar en la posición 5.000, primero tienes que llegar ahí, y eso es O(n). En el arreglo también es O(n), pero por otra razón (desplazar), y desplazar memoria contigua es muchísimo más rápido que perseguir punteros.

**Segunda: la localidad de caché.** El procesador no lee bytes sueltos de la RAM: trae bloques (líneas de caché, típicamente de 64 bytes) y además predice qué vas a leer después. Recorrer un arreglo es el mejor caso posible: cada línea trae varios elementos y el siguiente bloque ya viene en camino. Recorrer una lista enlazada es el peor: cada nodo puede estar en cualquier lado del heap, cada salto es un posible fallo de caché, y el prefetcher no puede adivinar a dónde apunta el siguiente puntero. A eso súmale el costo de memoria: cada nodo carga uno o dos punteros y, en lenguajes como Java o Python, el encabezado de un objeto.

Resultado: para la gran mayoría de los usos, un arreglo dinámico le gana a una lista enlazada incluso en operaciones donde la teoría dice lo contrario. Bjarne Stroustrup lo mostró con un experimento conocido en su charla de GoingNative 2012: insertar números en orden en una secuencia (buscando la posición linealmente) y después borrarlos fue mucho más rápido con `vector` que con `list`, aunque la lista "debería" ganar en inserciones.

**Dónde sí gana una lista enlazada:**

- Cuando **ya tienes el puntero al nodo** y necesitas sacarlo o moverlo en O(1). El ejemplo canónico es la [caché LRU](/casos/listas-enlazadas): un diccionario apunta a cada nodo y la lista doble mantiene el orden de uso. En Java, `LinkedHashMap` con orden de acceso y `removeEldestEntry` ya hace exactamente eso.
- Cuando necesitas que las referencias a los elementos **no se invaliden** al insertar (en un arreglo, crecer mueve todo).
- Colas concurrentes sin locks y listas intrusivas en sistemas operativos.

En Java, `LinkedList` implementa `List` y `Deque`, pero casi nunca es la mejor opción: para pilas y colas, la documentación de `ArrayDeque` (un arreglo circular) dice que probablemente sea más rápida que `Stack` como pila y que `LinkedList` como cola. `collections.deque` de Python es un caso intermedio interesante: una lista doblemente enlazada de **bloques** de elementos, que recupera parte de la localidad de caché y da O(1) en ambos extremos.

## La tabla hash por dentro

Es la estructura más preguntada, porque está detrás de `dict`, `HashMap`, `Map`, `set` y de la mitad de las soluciones de live coding. Conviene saber contarla en cinco piezas.

**1. La función hash.** Convierte la llave en un número. Tiene que ser **determinista** (la misma llave da siempre el mismo número), **rápida** y **repartir bien** (llaves parecidas deberían caer lejos). Ese número se reduce a una posición del arreglo de buckets: `hash(llave) % capacidad`, o con una máscara de bits si la capacidad es potencia de 2, que es lo que hace `HashMap`.

**2. Las colisiones.** Si hay más llaves posibles que buckets (siempre las hay), dos llaves distintas van a caer en el mismo bucket. No es un error: es parte del diseño. Hay dos familias de soluciones:

- **Encadenamiento** (*separate chaining*): cada bucket guarda una lista de pares. Si choca, se agrega a la lista. Es lo que hace `HashMap` de Java. Es simple y tolera factores de carga altos, pero cada bucket es una estructura aparte (otra vez, punteros y fallos de caché).
- **Direccionamiento abierto** (*open addressing*): todo vive en el mismo arreglo. Si el bucket está ocupado, se prueba otro siguiendo una secuencia: el siguiente (sondeo lineal), saltos crecientes (cuadrático) o un segundo hash. Es lo que hace el `dict` de CPython, con una secuencia de sondeo que mezcla bits altos del hash. Aprovecha mejor la caché, pero se degrada rápido cuando la tabla se llena, y **borrar** es delicado: no puedes vaciar la celda, porque cortarías la cadena de sondeo de otras llaves; se marca con una "lápida" (*tombstone*).

**3. El factor de carga.** `α = llaves / buckets`. Mide qué tan llena está la tabla. Con encadenamiento, `α` es el largo promedio de las cadenas; con direccionamiento abierto, determina cuántos sondeos esperas. Java `HashMap` crece cuando `α` pasa de 0,75; CPython, cuando el `dict` llega a dos tercios.

**4. El rehash.** Al pasar el umbral, se reserva un arreglo más grande (típicamente el doble) y **cada llave se vuelve a insertar**, porque `hash % capacidad` cambia con la capacidad. Es O(n), pero por el mismo argumento del arreglo dinámico, el costo amortizado por inserción sigue siendo O(1).

**5. El peor caso.** Si todas las llaves caen en el mismo bucket, buscar es recorrer una lista: **O(n)**. Pasa con una función hash mala o con un atacante que elige llaves que chocan a propósito (*hash flooding*). Por eso Python aleatoriza el hash de cadenas en cada proceso y usa SipHash, y Java 8 convierte en árbol rojo-negro los buckets que crecen demasiado, para que el peor caso dentro de un bucket sea O(log n).

Prueba el laboratorio: inserta hasta pasar el umbral para ver el rehash, cambia a sondeo lineal para ver cómo se forman racimos, y elige la función mala para ver cómo todo cae en pocos buckets.

### `HashMap` de Java, en concreto

Las cinco piezas, con los números reales de `HashMap` (verificables en su código fuente):

- **Capacidad inicial 16**, siempre potencia de 2. La tabla no se crea hasta el primer `put`.
- **Índice**: `(h ^ (h >>> 16)) & (capacidad − 1)`, con `h = key.hashCode()`. La máscara solo mira los bits bajos, así que antes mezcla los 16 bits altos con los bajos: dos hashes que solo difieren arriba no terminan siempre en el mismo bucket.
- **Factor de carga 0,75**: con 16 buckets, el `put` número 13 duplica la tabla a 32. En el resize, cada llave queda en su mismo índice o en `índice + capacidad vieja`, según un bit más del hash; no hace falta recalcular `hashCode()`.
- **Colisiones por encadenamiento**, y desde Java 8 con una defensa: cuando un bucket pasa de **8** nodos y la tabla tiene al menos **64** buckets, ese bucket se convierte en un **árbol rojo-negro**, y buscar ahí cuesta O(log n) en vez de O(n). Si la tabla es más chica, en vez de eso se duplica. Si en un resize el bucket baja a 6 nodos o menos, vuelve a ser una lista.
- Acepta **una** llave `null` (va al bucket 0). El orden de iteración no está definido y puede cambiar después de un resize: si necesitas el orden de inserción, `LinkedHashMap`; si necesitas orden por llave, `TreeMap`.

### Por qué las llaves deben ser inmutables

La posición de una llave se calcula **una vez**, al insertarla. Si después la llave cambia, su hash cambia, pero la entrada sigue en el bucket viejo. Al buscarla, la tabla calcula el hash nuevo, va a otro bucket y no la encuentra. La entrada queda perdida: ocupa memoria, no se puede consultar ni borrar.

Por eso Python no deja usar una `list` como llave (`TypeError: unhashable type: 'list'`) pero sí una `tuple`. En Java nada te lo impide: si usas como llave un objeto con `hashCode()` basado en campos mutables y los cambias, el bug es silencioso. La regla, en ambos lenguajes: **si dos objetos son iguales según `equals`/`__eq__`, deben tener el mismo hash**, y ese hash no puede cambiar mientras el objeto esté dentro de una tabla. En Java, si sobrescribes `equals`, sobrescribe también `hashCode` con los mismos campos; un `record` genera los dos.

<CodeTabs>

```java title="Java"
record Pedido(String pais, int numero) {} // inmutable: equals y hashCode por valor

void ejemplo() {
    Map<Pedido, String> estado = new HashMap<>();
    estado.put(new Pedido("MX", 1042), "en camino");
    System.out.println(estado.get(new Pedido("MX", 1042))); // en camino

    List<Integer> clave = new ArrayList<>(List.of(1, 2));
    Map<List<Integer>, String> roto = new HashMap<>();
    roto.put(clave, "x");
    clave.add(3); // la llave cambia, y su hashCode también
    System.out.println(roto.get(clave)); // null: busca en otro bucket
    System.out.println(roto.containsKey(List.of(1, 2))); // false: mismo hash, pero equals ya no
    System.out.println(roto.size()); // 1: la entrada sigue ahí, inalcanzable
}
```

```python title="Python"
pedido = ["MX", 1042]
indice = {}
indice[tuple(pedido)] = "en camino"   # bien: la tupla no puede cambiar
indice[pedido] = "en camino"          # TypeError: unhashable type: 'list'
```

</CodeTabs>

## Árboles balanceados y árboles B

Una tabla hash es rapidísima para "¿está esta llave?", pero **no sabe nada del orden**. No puede responder "dame el siguiente pedido después del 1042", "todas las ventas entre el 1 y el 15 de marzo" ni "el menor precio mayor que 100". Para eso están los **árboles de búsqueda balanceados** (rojo-negro, AVL): mantienen las llaves ordenadas y garantizan altura O(log n), así que buscar, insertar, borrar, encontrar el mínimo, el sucesor o un rango cuestan O(log n) (más k para devolver k resultados).

`TreeMap` y `TreeSet` en Java y `std::map` en C++ son árboles rojo-negro. Python no trae uno en la biblioteca estándar; se usa `bisect` sobre una lista ordenada (inserción O(n)) o la librería `sortedcontainers`.

**Hash o árbol.** Si solo necesitas pertenencia o búsqueda exacta, hash: O(1) promedio contra O(log n). Si necesitas orden, rangos o "el más cercano", árbol. Y si necesitas el peor caso garantizado, árbol también: no tiene la degradación a O(n) de un hash con colisiones.

### Por qué las bases de datos usan árboles B+

Un **árbol B** cambia la forma del árbol para minimizar las lecturas: cada nodo ocupa una página completa del disco (8 KB en PostgreSQL, 16 KB por defecto en InnoDB de MySQL) y guarda **cientos de llaves** con sus punteros a hijos. Con un factor de ramificación tan alto, el árbol es bajísimo. Supongamos 500 llaves por nodo: tres niveles alcanzan para 500³ = 125 millones de llaves, y cuatro para 62.500 millones. Además, los niveles superiores son pocos y se quedan en memoria, así que buscar una fila suele costar una o dos lecturas reales de disco.

El **árbol B+**, la variante que usan casi todas las bases relacionales, agrega dos cosas:

- **Los datos (o los punteros a las filas) viven solo en las hojas.** Los nodos internos guardan solo llaves de guía, así que caben más por página y el árbol es todavía más bajo.
- **Las hojas están enlazadas entre sí** en orden. Una consulta por rango (`WHERE fecha BETWEEN …`, `ORDER BY`, `LIMIT`) baja una vez hasta la primera hoja y después recorre hojas vecinas en secuencia, sin volver a subir.

¿Y por qué no un índice hash? Existen (PostgreSQL los tiene), pero solo sirven para igualdad: no ayudan con rangos, `ORDER BY`, prefijos (`LIKE 'abc%'`) ni con índices compuestos usados por su primera columna. El árbol B+ cubre todos esos casos con un costo casi igual para la búsqueda exacta. Por eso es el tipo de índice por defecto. Hay más sobre índices en [bases de datos](/system-design/bases-de-datos).

## Heap, trie, grafo, set y map

**Heap (montículo binario).** Un árbol binario completo guardado en un arreglo, sin punteros: los hijos de `i` están en `2i + 1` y `2i + 2`, y el padre en `(i − 1) // 2`. Solo garantiza que cada padre es menor (o mayor) que sus hijos, no un orden total. Eso basta para lo que hace: ver el mínimo en O(1), insertar y extraer el mínimo en O(log n), y construirse a partir de n elementos en O(n). **No sirve para buscar** un elemento arbitrario (O(n)). Se usa para colas de prioridad, top-K, planificadores y Dijkstra. En Java es `PriorityQueue`, un min-heap por defecto (para un max-heap, `Collections.reverseOrder()`); en Python, `heapq`. Lo ves en acción en [heaps y top-K](/casos/heaps-y-top-k) y en el problema de las salas de [intervalos](/casos/intervalos-y-greedy).

**Trie (árbol de prefijos).** Cada arista es un carácter y cada camino desde la raíz es un prefijo. Buscar, insertar o preguntar "¿hay palabras que empiecen con…?" cuesta O(L), con L el largo de la palabra, **sin importar cuántas palabras hay**. El costo es la memoria: muchos nodos con pocos hijos. Es la base del [autocompletado](/casos/autocompletado) y del corrector ortográfico; también aparece en tablas de ruteo IP. Si solo necesitas búsquedas exactas, un set de hash es más simple y más compacto.

**Grafo.** Dos representaciones. La **lista de adyacencia** (un diccionario de nodo a lista de vecinos) usa O(V + E) memoria y recorre los vecinos de un nodo en O(grado): es la elección por defecto, porque la mayoría de los grafos reales son dispersos (una red social tiene millones de usuarios, pero cada uno conecta con pocos cientos). La **matriz de adyacencia** usa O(V²) memoria y responde "¿hay arista entre u y v?" en O(1): conviene con grafos densos o chicos. Los recorridos están en [grafos](/casos/grafos).

**Set contra map.** Un set es un map sin valores: guarda solo llaves y responde "¿está?". Por dentro son la misma estructura; en Java, `HashSet` está implementado sobre un `HashMap`. Ambos vienen en sabor hash (`HashSet`/`HashMap`: sin orden, O(1) promedio) y en sabor árbol (`TreeSet`/`TreeMap`: ordenado, O(log n)). En JavaScript, prefiere `Map` y `Set` sobre objetos planos cuando las llaves son dinámicas: aceptan llaves de cualquier tipo, conservan el orden de inserción y no chocan con propiedades heredadas como `constructor`.

Todos los costos son de tiempo. "Prom." es caso promedio con una buena función hash; "amort." es costo amortizado.

Dos advertencias para cuando la recites. La primera: Big-O esconde constantes, y en la práctica la localidad de caché pesa muchísimo (por eso el arreglo le gana a la lista enlazada aunque la tabla diga lo contrario). La segunda: el "O(1)" de la tabla hash supone que calcular el hash es O(1), pero hashear una cadena de largo L cuesta O(L). Con llaves largas, ese costo domina.

## Cómo lo preguntan

Estas aparecen una y otra vez. Las respuestas modelo están pensadas para decirse en 30 a 60 segundos; después, el entrevistador elige por dónde profundizar.

### "¿Qué pasa cuando haces `map.put(key, value)` en un `HashMap`?"

> "Java llama a `key.hashCode()` y mezcla los 16 bits altos con los bajos, porque el índice sale de una máscara: `(capacidad − 1) & hash`, con una capacidad que siempre es potencia de 2. Si ese bucket está vacío, crea un nodo ahí. Si no, recorre la cadena comparando primero el hash y después la llave con `equals`: si la encuentra, reemplaza el valor y devuelve el anterior; si no, agrega un nodo al final. Si esa cadena pasa de 8 nodos y la tabla tiene al menos 64 buckets, la convierte en un árbol rojo-negro. Al final, si el tamaño supera capacidad × 0,75, duplica la tabla y redistribuye. En promedio es O(1), amortizado por los resize; con muchas colisiones, los árboles limitan el daño a O(log n) dentro de un bucket."

Puntos que suman: el contrato entre `equals` y `hashCode` (y qué se rompe si solo sobrescribes uno), que `put` devuelve el valor anterior o `null`, que acepta una llave `null`, y que reservar la capacidad con `HashMap.newHashMap(n)` evita los resize.

### "¿Y en Python, con `dict[key] = v`?"

> "Python calcula `hash(key)`, que para un string ya viene cacheado en el objeto. Con los bits bajos de ese hash elige una posición en la tabla. Si está vacía, guarda ahí el par. Si está ocupada, compara: primero el hash guardado y después la llave con `==`. Si es la misma llave, reemplaza el valor; si es otra, es una colisión, y sigue probando otras posiciones con una secuencia de sondeo que mezcla los bits altos del hash, porque CPython usa direccionamiento abierto. Después de insertar, si la tabla quedó llena en más de dos tercios, reserva una más grande y reinserta todo. En promedio es O(1); el rehash ocasional es O(n) pero amortizado sigue siendo O(1); y el peor caso, si todo colisiona, es O(n)."

Puntos que suman: mencionar que la llave tiene que ser hasheable (y por qué), que desde Python 3.7 el `dict` conserva el orden de inserción porque guarda las entradas en un arreglo compacto aparte de la tabla de índices, y que el hash de strings se aleatoriza por proceso para evitar ataques.

### "¿Arreglo o lista enlazada para X?"

> "Mi respuesta por defecto es el arreglo dinámico, un `ArrayList` en Java: acceso O(1) por índice, append O(1) amortizado y, sobre todo, memoria contigua, que el procesador recorre mucho más rápido que una cadena de punteros. Elegiría una lista enlazada solo si necesito insertar o sacar elementos en el medio **teniendo ya la referencia al nodo**, como en una caché LRU, o si necesito que las referencias a los elementos sigan siendo válidas cuando la colección crece. Si lo que necesito es insertar en los dos extremos, uso una deque, `ArrayDeque` en Java; `LinkedList` casi nunca."

Lo que el entrevistador quiere oír es que la respuesta **depende de las operaciones**, y que conoces el costo oculto de la lista enlazada (buscar la posición sigue siendo O(n), y la caché).

### "¿Por qué un HashMap no es thread-safe?"

> "Porque sus operaciones no son atómicas: un `put` lee el bucket, compara, escribe, actualiza el contador de tamaño y a veces dispara un resize que mueve todas las entradas. Si dos hilos hacen `put` al mismo tiempo, uno puede pisar la escritura del otro y se pierden datos; si uno lee mientras otro hace el resize, puede ver la tabla a medio construir. En Java 7, un resize concurrente podía incluso dejar un ciclo en una cadena y un `get` quedaba en un loop infinito. La solución es no compartirlo, o usar una estructura pensada para eso: `ConcurrentHashMap` en Java, que permite lecturas sin bloqueo y escrituras con bloqueos finos por bucket, en vez de un lock global como `Collections.synchronizedMap`."

<CodeTabs>

```java title="Java"
final ConcurrentHashMap<String, Integer> conteo = new ConcurrentHashMap<>();

void registrar(String palabra) {
    conteo.merge(palabra, 1, Integer::sum); // atómico: leer, sumar y escribir en un paso
    // conteo.put(palabra, conteo.getOrDefault(palabra, 0) + 1); // NO: otro hilo se mete en medio
}
```

```python title="Python"
from collections import Counter
from threading import Lock

conteo = Counter()
candado = Lock()

def registrar(palabra: str) -> None:
    with candado:  # += es leer y escribir: sin el lock se pierden incrementos
        conteo[palabra] += 1
```

</CodeTabs>

Si el entrevistador viene de otro lenguaje: en Go, si varias goroutines escriben en un `map` sin sincronizar, el runtime suele detectarlo y aborta el programa con un error de escrituras concurrentes (`sync.Map` o un mutex lo resuelven). En CPython con GIL, una operación suelta sobre un `dict` es atómica en la práctica, pero `conteo[k] += 1` no lo es: son una lectura y una escritura separadas, y otro hilo puede meterse entre las dos.

<Takeaways>

- El arreglo dinámico tiene **append O(1) amortizado** porque la capacidad crece en proporción: las copias suman menos que 2n. Con crecimiento fijo, el promedio sube sin parar.
- La lista enlazada pierde contra el arreglo en casi todo por la **localidad de caché**; gana cuando ya tienes la referencia al nodo, como en una caché LRU.
- Una tabla hash es función hash + buckets + resolución de colisiones + factor de carga + rehash. Es **O(1) promedio**, **O(n) en el peor caso**, y sus llaves deben ser inmutables.
- Hash para búsqueda exacta; **árbol balanceado** cuando necesitas orden, rangos o vecinos, con O(log n) garantizado.
- Las bases de datos usan **árboles B+** porque minimizan lecturas de disco (nodos del tamaño de una página, altura de 3 o 4) y sirven para rangos gracias a las hojas enlazadas.
- Una buena respuesta teórica sigue el orden **mecanismo, costo, peor caso, cuándo usarlo**, y cabe en un minuto.
