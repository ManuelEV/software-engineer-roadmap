"¿Cuáles son los pilares de la programación orientada a objetos?" es probablemente la pregunta técnica más repetida en entrevistas para puestos junior y semi senior de Latinoamérica. Y "explícame SOLID" la sigue de cerca. Parecen preguntas de memoria, y por eso mucha gente las responde como si recitara un glosario: "encapsulamiento es ocultar los datos, herencia es reutilizar código". Esa respuesta no está mal, pero tampoco te diferencia de nadie.

Lo que el entrevistador busca es otra cosa: que entiendas **para qué sirve** cada idea, que sepas cuándo **no** aplicarla y que puedas aterrizarla en código que escribiste. Este tema es la versión de entrevista de lo que la [unidad de patrones](/patrones/introduccion) cubre a fondo: cómo se pregunta, respuestas que se pueden decir en 30 a 60 segundos y ejemplos lo bastante cortos para escribirlos en una pizarra.

## Cómo se pregunta (y qué están evaluando)

Estas preguntas aparecen en cuatro formatos, y conviene reconocerlos porque cada uno pide una respuesta distinta:

1. **Definición directa.** "¿Qué es polimorfismo?", "¿interfaz o clase abstracta?". Responde con una definición de una frase, un ejemplo concreto y un matiz. Treinta segundos.
2. **Comparación.** "Composición contra herencia", "DI contra DIP". El entrevistador quiere el criterio para elegir, no dos definiciones paralelas.
3. **Código para revisar.** Te muestran una clase y preguntan "¿qué le cambiarías?". Aquí SOLID funciona como lente para diagnosticar, no como lista para recitar.
4. **Conductual-técnica.** "¿Cómo aplicaste SOLID en un proyecto?". Quieren una historia real con un antes, un después y un resultado.

<Callout type="interview" title="Lo que el entrevistador está evaluando aquí">

Tres cosas: que la definición sea **correcta** (muchos confunden abstracción con encapsulamiento, o inversión con inyección de dependencias), que puedas dar un **ejemplo propio** en lugar del de animales y figuras, y que muestres **criterio**: cuándo un principio ayuda y cuándo agrega complejidad. En semi senior y senior, el tercer punto pesa más que los otros dos.

</Callout>

## Los cuatro pilares, sin glosario

### Encapsulamiento: proteger invariantes

Encapsular no es "poner los atributos privados y generar getters y setters". Es que el objeto **controle sus propias reglas**: que nadie desde afuera pueda dejarlo en un estado inválido. Una clase con todos sus campos privados y un setter por campo no encapsula nada; solo agrega ceremonia.

<CodeTabs>

```java title="Java"
public class Cuenta {
    private long saldo; // privado: el único camino para cambiarlo es retirar()

    public Cuenta(long saldoInicial) {
        if (saldoInicial < 0) throw new IllegalArgumentException("Saldo inicial negativo");
        this.saldo = saldoInicial;
    }

    public long getSaldo() {
        return saldo;
    }

    public void retirar(long monto) {
        if (monto <= 0) throw new IllegalArgumentException("El monto debe ser positivo");
        if (monto > saldo) throw new IllegalStateException("Saldo insuficiente");
        saldo -= monto;
    }
}
```

```python title="Python"
class Cuenta:
    def __init__(self, saldo_inicial: int) -> None:
        self._saldo = saldo_inicial  # convención: no lo toques desde afuera

    @property
    def saldo(self) -> int:
        return self._saldo

    def retirar(self, monto: int) -> None:
        if monto <= 0:
            raise ValueError("el monto debe ser positivo")
        if monto > self._saldo:
            raise ValueError("saldo insuficiente")
        self._saldo -= monto
```

```ts title="TypeScript"
class Cuenta {
  #saldo: number // privado de verdad en runtime (campo # de JavaScript)

  constructor(saldoInicial: number) {
    this.#saldo = saldoInicial
  }

  get saldo() {
    return this.#saldo
  }

  retirar(monto: number) {
    if (monto <= 0) throw new Error('El monto debe ser positivo')
    if (monto > this.#saldo) throw new Error('Saldo insuficiente')
    this.#saldo -= monto
  }
}
```

</CodeTabs>

El invariante ("el saldo nunca es negativo") vive en un solo lugar. Si existiera `setSaldo()`, cualquier parte del sistema podría romperlo. Un buen matiz para decir en voz alta: en Java `private` lo hace cumplir el compilador (aunque la reflexión puede saltárselo), en Python la privacidad es una **convención** (el guion bajo) y en TypeScript el modificador `private` desaparece al compilar, mientras que los campos `#` de JavaScript sí son privados en tiempo de ejecución.

### Abstracción: exponer el qué, esconder el cómo

Abstraer es elegir qué detalles importan para quien usa algo. `PasarelaDePago.cobrar(cliente, monto)` es una abstracción: el checkout no sabe si detrás hay Stripe, MercadoPago o un fake de tests. La diferencia con el encapsulamiento es sutil y la preguntan: **la abstracción decide qué mostrar** (el diseño del contrato), **el encapsulamiento impide tocar lo que no se muestra** (la protección del estado).

### Herencia: "es un", con contrato

La herencia permite que una clase reutilice y especialice a otra. Es la herramienta más sobreutilizada de la POO porque se enseña primero y con ejemplos donde funciona (`Perro extends Animal`). En código real, la herencia acopla a la subclase con los **detalles internos** de la base, y eso trae los problemas que verás más abajo.

### Polimorfismo: dinámico y estático

Polimorfismo es que el mismo mensaje produzca comportamientos distintos según quién lo recibe. Hay dos formas, y separarlas es una buena señal:

- **Dinámico** (de subtipos): se decide en **tiempo de ejecución** qué método corre, según el tipo real del objeto. Es la sobrescritura (*override*). Una lista de `Notificador` puede tener emails y SMS, y `n.enviar()` llama al correcto.
- **Estático** (*ad hoc* y paramétrico): se decide en **tiempo de compilación**. La sobrecarga (*overloading*: mismo nombre, distintos parámetros) y los genéricos (`List<T>`).

<CodeTabs>

```java title="Java"
import java.time.LocalDate;
import java.util.List;

interface Notificador {
    void enviar(String mensaje);
}

class Email implements Notificador {
    @Override
    public void enviar(String mensaje) {
        System.out.println("email: " + mensaje);
    }
}

class Sms implements Notificador {
    @Override
    public void enviar(String mensaje) {
        System.out.println("sms: " + mensaje.substring(0, Math.min(160, mensaje.length())));
    }
}

class Avisos {
    static void avisar(List<Notificador> canales) {
        for (Notificador n : canales) n.enviar("Tu pedido salió"); // dinámico: decide el objeto
    }
}

class Formato {
    // Sobrecarga real: el compilador elige según el tipo del argumento
    static String formatear(double valor) {
        return String.format("%.2f", valor);
    }

    static String formatear(LocalDate fecha) {
        return fecha.toString();
    }
}
```

```python title="Python"
from functools import singledispatch

class Notificador:
    def enviar(self, mensaje: str) -> None: ...

class Email(Notificador):
    def enviar(self, mensaje: str) -> None:
        print(f"email: {mensaje}")

class Sms(Notificador):
    def enviar(self, mensaje: str) -> None:
        print(f"sms: {mensaje[:160]}")

for n in [Email(), Sms()]:
    n.enviar("Tu pedido salió")   # dinámico: decide el objeto

# Python no tiene sobrecarga real: la última definición gana.
# singledispatch elige la función según el tipo del primer argumento.
@singledispatch
def formatear(valor) -> str:
    return str(valor)

@formatear.register
def _(valor: float) -> str:
    return f"{valor:.2f}"
```

```ts title="TypeScript"
interface Notificador {
  enviar(mensaje: string): void
}
class Email implements Notificador {
  enviar(mensaje: string) { console.log(`email: ${mensaje}`) }
}
class Sms implements Notificador {
  enviar(mensaje: string) { console.log(`sms: ${mensaje.slice(0, 160)}`) }
}

for (const n of [new Email(), new Sms()]) n.enviar('Tu pedido salió') // dinámico

// Sobrecarga en TS: varias firmas, UNA implementación que distingue en runtime
function formatear(valor: number): string
function formatear(valor: Date): string
function formatear(valor: number | Date): string {
  return valor instanceof Date ? valor.toISOString() : valor.toFixed(2)
}
```

</CodeTabs>

El matiz por lenguaje vale puntos: Java y C# tienen sobrecarga real, resuelta por el compilador. TypeScript solo tiene **firmas** sobrecargadas sobre una única implementación. Python no tiene sobrecarga: `typing.overload` solo informa al chequeador de tipos, y en tiempo de ejecución se usa `functools.singledispatch`.

## Interfaz contra clase abstracta

La respuesta corta: **una interfaz define un contrato** (qué se puede hacer) y **una clase abstracta comparte una implementación parcial** (estado y código común) entre subclases que son de la misma familia. Una clase puede cumplir varios contratos, pero en Java y TypeScript solo puede heredar de una clase.

La respuesta que suma puntos agrega los matices del lenguaje, porque cambiaron con el tiempo:

| | Java | TypeScript | Python |
| --- | --- | --- | --- |
| Interfaz | `interface`. Desde Java 8 admite métodos `default` y `static`, pero no estado de instancia. Una clase implementa varias. | `interface`: solo existe para el compilador y desaparece en el JavaScript generado. Es **estructural**: cumple quien tenga la forma, sin `implements`. | No hay palabra clave. `typing.Protocol` define un contrato estructural que verifica el chequeador de tipos (mypy, pyright). |
| Clase abstracta | `abstract class`: puede tener estado, constructor y métodos `protected`. Herencia simple. | `abstract class`: existe en tiempo de ejecución y puede tener implementación. Herencia simple. | `abc.ABC` con `@abstractmethod`: no se puede instanciar si falta implementar un método. Python permite herencia múltiple. |

Cuándo usar cada una:

- **Interfaz** cuando tipos no relacionados comparten una capacidad: `Comparable`, `Exportable`, `PasarelaDePago`. Es lo que inyectas y lo que mockeas en tests.
- **Clase abstracta** cuando hay un esqueleto común con pasos que cambian. Es el patrón [*Template Method*](/patrones/comportamiento-2): `Reporte.generar()` arma encabezado, cuerpo y pie, y cada subclase solo define `cuerpo()`.

<Callout type="tip" title="El matiz de Java 8">

Si te preguntan "¿y ahora que las interfaces tienen métodos `default`, qué diferencia queda?", la respuesta es el **estado**: una interfaz no puede tener campos de instancia ni constructor. Los métodos `default` existen para evolucionar interfaces sin romper a quienes ya las implementan (así se agregó `forEach` a `Iterable` en Java 8), no para reemplazar a las clases abstractas.

</Callout>

<Callout type="tip" title="En Java">

Una clase que no fue diseñada para heredarse debería ser `final` (*Effective Java*, ítem 19: "diseña y documenta para la herencia, o prohíbela"). Desde Java 17 existe un punto intermedio: las clases e interfaces `sealed`, que enumeran exactamente quién puede extenderlas (`sealed interface Pago permits Tarjeta, Transferencia`). Es un buen matiz para cerrar la respuesta.

</Callout>

## Composición contra herencia

"Prefiere la composición sobre la herencia" viene del libro del GoF de 1994, y el tema de [introducción a patrones](/patrones/introduccion) lo desarrolla. Para la entrevista necesitas dos cosas: un ejemplo de herencia que se rompe y un criterio para cuándo sí heredar.

### El ejemplo clásico: la clase base frágil

Joshua Bloch lo usa en *Effective Java* (ítem 18 de la tercera edición). Quieres contar cuántos elementos se agregaron a un `HashSet`, así que heredas y sobrescribes los dos métodos que agregan:

```java title="InstrumentedHashSet.java"
public class InstrumentedHashSet<E> extends HashSet<E> {
    private int addCount = 0;

    @Override public boolean add(E e) {
        addCount++;
        return super.add(e);
    }

    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);
    }

    public int getAddCount() { return addCount; }
}

var s = new InstrumentedHashSet<String>();
s.addAll(List.of("a", "b", "c"));
s.getAddCount(); // 6, no 3
```

¿Por qué 6? Porque la implementación de `addAll` que hereda `HashSet` llama internamente a `add` por cada elemento, y ese `add` es el tuyo, que vuelve a contar. Tu subclase depende de un **detalle de implementación** de la clase base que no está en su contrato y que puede cambiar en la próxima versión del JDK. Eso es la *clase base frágil*.

La solución con composición: una clase que **tiene** un `Set` y le reenvía las llamadas. Sus `add` y `addAll` cuentan y delegan; lo que el `Set` interno haga por dentro ya no importa.

```java title="InstrumentedSet.java"
public class InstrumentedSet<E> extends ForwardingSet<E> { // ForwardingSet delega todo en un Set interno
    private int addCount = 0;
    public InstrumentedSet(Set<E> s) { super(s); }

    @Override public boolean add(E e) { addCount++; return super.add(e); }
    @Override public boolean addAll(Collection<? extends E> c) { addCount += c.size(); return super.addAll(c); }
}
```

Ahora `super.addAll` llama al `addAll` del set envuelto, que llama a **su propio** `add`, no al tuyo. Y de yapa, `InstrumentedSet` funciona con cualquier `Set`: `HashSet`, `TreeSet` o el que sea.

### El otro problema: varios ejes de variación

El segundo argumento contra la herencia aparece cuando el sistema crece en más de una dimensión. Recorre el widget: cada requisito nuevo es razonable, y aun así la jerarquía explota.

<InheritanceBreaker />

Fíjate en el requisito 4. Además de la explosión combinatoria, la herencia fija el comportamiento **al crear el objeto**: un repartidor no puede pasar de moto a bici sin convertirse en otro objeto. Con composición, el comportamiento es un campo que se puede reemplazar en tiempo de ejecución. Esa es exactamente la idea del patrón [*Strategy*](/patrones/comportamiento-1).

**¿Cuándo sí heredar?** Cuando la relación es un "es un" estable, la subclase respeta por completo el contrato de la base (Liskov) y quieres reutilizar un esqueleto controlado por la base, como en Template Method o en los frameworks que te piden extender una clase (`Exception`, un `Activity` de Android, un `TestCase`). Cuando la base es **de otro equipo o de una librería** y no fue diseñada para extenderse, la composición casi siempre es más segura.

<Callout type="example" title="Respuesta modelo (50 segundos)">

"La herencia acopla la subclase a los detalles internos de la base y fija el comportamiento al crear el objeto. Si la base cambia cómo se implementa algo, la subclase puede romperse sin haber cambiado: el ejemplo clásico es heredar de `HashSet` para contar inserciones, donde `addAll` llama a `add` y cuentas el doble. Y cuando hay dos ejes de variación, como vehículo y tipo de carga, la herencia necesita una subclase por combinación. Con composición, el objeto tiene sus comportamientos como campos, cada eje varía por separado y puedo cambiarlos en tiempo de ejecución. Heredo cuando hay un 'es un' estable y la base está diseñada para extenderse, como un Template Method."

</Callout>

## SOLID en versión de entrevista

Los cinco principios están explicados con código antes y después en [Qué es un patrón (y SOLID)](/patrones/introduccion), con un widget que muestra cuántos archivos toca cada cambio. Aquí va la versión compacta: una definición que puedas decir de memoria, un ejemplo mínimo y el error típico al explicarlo.

### S: responsabilidad única

**Definición:** un módulo debería tener una sola razón para cambiar; en la formulación de Robert C. Martin, responder a **un solo actor** (un grupo de personas que pide cambios).

<CodeTabs>

```java title="Java"
// Antes: Finanzas, Diseño e Infraestructura piden cambios a la misma clase
interface FacturaTodoEnUno {
    BigDecimal total();
    byte[] aPdf();
    void guardar();
}

// Después: la factura son datos y cada actor tiene su módulo
record Factura(List<Linea> lineas) {}
interface CalculadoraFactura { BigDecimal total(Factura f); }
interface PdfFactura { byte[] generar(Factura f); }
interface RepositorioFacturas { void guardar(Factura f); }
```

```ts title="TypeScript"
// Antes: Finanzas, Diseño e Infraestructura piden cambios a la misma clase
class Factura { total() {} aPdf() {} guardar() {} }
// Después: cada actor tiene su módulo
class CalculadoraFactura { total(f: Factura) {} }
class PdfFactura { generar(f: Factura) {} }
class RepositorioFacturas { guardar(f: Factura) {} }
```

</CodeTabs>

**Error típico:** decir "una clase debe hacer una sola cosa". ¿Qué es una cosa? Con esa regla, cada método termina en su propia clase.

### O: abierto/cerrado

**Definición:** abierto a extensión, cerrado a modificación. Cuando aparece un caso nuevo, lo **agregas** en lugar de editar código que ya funciona.

<CodeTabs>

```java title="Java"
class Envios {
    // Antes: cada transportista nuevo edita este switch
    static int costo(Pedido p) {
        return switch (p.transportista()) {
            case "dhl" -> 50 + p.pesoKg() * 4;
            case "fedex" -> 45 + p.pesoKg() * 5;
            default -> throw new IllegalArgumentException(p.transportista());
        };
    }

    // Después: un transportista nuevo es una clase nueva
    static final Map<String, Transportista> TRANSPORTISTAS = Map.of("dhl", new Dhl(), "fedex", new Fedex());
}

interface Transportista {
    int costo(Pedido p);
}
```

```ts title="TypeScript"
// Antes: cada transportista nuevo edita este switch
function costo(p: Pedido) { switch (p.transportista) { case 'dhl': /* ... */ } }
// Después: un transportista nuevo es una clase nueva
interface Transportista { costo(p: Pedido): number }
const transportistas: Record<string, Transportista> = { dhl: new Dhl(), fedex: new Fedex() }
```

</CodeTabs>

**Error típico:** abrir todos los ejes por adelantado. Solo se abre un eje que ya cambió o que el negocio anunció.

### L: sustitución de Liskov

**Definición:** si `S` es subtipo de `T`, cualquier código que funciona con un `T` debe seguir funcionando con un `S`, sin sorpresas.

<CodeTabs>

```java title="Java"
class Pago {
    void reembolsar(long monto) { /* devuelve el dinero */ }
}

class PagoGiftCard extends Pago {
    @Override
    void reembolsar(long monto) {
        throw new UnsupportedOperationException("No soportado"); // rompe el contrato de Pago
    }
}
```

```ts title="TypeScript"
class Pago { reembolsar(monto: number) { /* ... */ } }
class PagoGiftCard extends Pago {
  reembolsar() { throw new Error('No soportado') } // rompe el contrato de Pago
}
```

</CodeTabs>

**Señal para reconocerlo:** un `if (x instanceof Subclase)` en el código cliente (en Java, también un `UnsupportedOperationException` en un método heredado). **Error típico:** quedarse en el ejemplo del cuadrado y el rectángulo sin poder dar uno propio.

### I: segregación de interfaces

**Definición:** ningún cliente debería depender de métodos que no usa. Las interfaces se diseñan desde quien las consume.

<CodeTabs>

```java title="Java"
// ReporteVentas solo necesita esto, no el repositorio de 8 métodos
interface PedidosPorFecha {
    List<Pedido> buscar(LocalDate desde, LocalDate hasta);
}
```

```ts title="TypeScript"
// ReporteVentas solo necesita esto, no el repositorio de 8 métodos
```

### D: inversión de dependencias

**Definición:** los módulos de alto nivel (el negocio) no dependen de los de bajo nivel (SDKs, bases de datos). Ambos dependen de una abstracción, y la abstracción **la define el alto nivel**.

```java title="Java"

    private final PasarelaDePago pagos;

        this.pagos = pagos;

    String pagar(String clienteId, long centavos) {
        return pagos.cobrar(clienteId, centavos);

    @Override
    public String cobrar(String clienteId, long centavos) {
        return "pi_123"; // aquí iría la llamada al SDK de Stripe
    }
}
```

### "¿Cómo aplicaste SOLID en un proyecto?"

Esta pregunta es conductual disfrazada de técnica. La respuesta débil suena así:

> "Siempre aplico SOLID. Uso interfaces para todo y cada clase tiene una sola responsabilidad. También uso inyección de dependencias."

No hay un problema, no hay un antes ni un después, no hay resultado, y "interfaces para todo" es una pequeña bandera roja. La respuesta fuerte cuenta un caso concreto con la estructura de una historia corta (la desarrollamos en [la entrevista conductual](/casos/entrevista-conductual)):

> "En una plataforma de e-commerce teníamos un `CheckoutService` que instanciaba directamente el cliente de MercadoPago. Cuando el negocio decidió agregar Stripe para clientes de Estados Unidos, el cambio tocaba la clase más crítica del sistema, y además no podíamos testearla sin llamar a la API de sandbox, así que los tests tardaban varios minutos y fallaban por red. Propuse definir una interfaz `PasarelaDePago` en el dominio, con el vocabulario nuestro (cobrar, reembolsar), y dos adaptadores. Es inversión de dependencias. Agregar Stripe pasó a ser un archivo nuevo más una línea en la configuración, y los tests de checkout pasaron a correr con un fake en memoria. Lo que **no** hice fue abstraer el envío de emails, que tenía un solo proveedor y nadie planeaba cambiar."

Fíjate en el cierre: mostrar dónde **decidiste no aplicar** un principio es lo que convence a un entrevistador senior de que lo entiendes.

## Inyección de dependencias e inversión de control

Tres términos que se confunden siempre, y que conviene separar con precisión:

- **Inversión de dependencias (DIP)** es un principio de diseño: hacia dónde apuntan las dependencias. El negocio define la interfaz; la infraestructura la implementa.
- **Inyección de dependencias (DI)** es una técnica: un objeto **recibe** sus colaboradores (por constructor, normalmente) en lugar de crearlos. Puedes inyectar una clase concreta y no estar aplicando DIP.
- **Inversión de control (IoC)** es la idea más general: el control del flujo lo tiene un framework, no tu código. "No nos llames, nosotros te llamamos". Un contenedor de DI (Spring, NestJS, .NET) es una forma de IoC; un framework web que llama a tus *handlers* es otra.

<CodeTabs>

```java title="Java"
interface Notificador {
    void enviar(String destino, String mensaje);
}

class ServicioPedidos {
    private final RepositorioPedidos repo;
    private final Notificador notificador;

    // DI por constructor: recibe sus dependencias, no las crea
    ServicioPedidos(RepositorioPedidos repo, Notificador notificador) {
        this.repo = repo;
        this.notificador = notificador;
    }

    void despachar(String pedidoId) {
        Pedido pedido = repo.buscar(pedidoId);
        pedido.despachar();
        repo.guardar(pedido);
        notificador.enviar(pedido.email(), "Tu pedido va en camino");
    }
}

// composition root: el único lugar que conoce las clases concretas
class App {
    public static void main(String[] args) {
        var servicio = new ServicioPedidos(new PostgresPedidos(dataSource()), new NotificadorSes(clienteSes()));
        // en tests, sin red ni base de datos:
        // new ServicioPedidos(new PedidosEnMemoria(), new NotificadorFalso())
    }
}
```


```ts title="TypeScript"
interface Notificador {
  enviar(destino: string, mensaje: string): Promise<void>
}

class ServicioPedidos {
  // DI por constructor: recibe sus dependencias, no las crea
  constructor(
    private readonly repo: RepositorioPedidos,
    private readonly notificador: Notificador,
  ) {}

  async despachar(pedidoId: string) {
    const pedido = await this.repo.buscar(pedidoId)
    pedido.despachar()
    await this.repo.guardar(pedido)
    await this.notificador.enviar(pedido.email, 'Tu pedido va en camino')
  }
}

// composition root: el único lugar que conoce las clases concretas
const servicio = new ServicioPedidos(new PostgresPedidos(pool), new NotificadorSes(ses))

// en tests, sin red ni base de datos
const servicioTest = new ServicioPedidos(new PedidosEnMemoria(), new NotificadorFalso())
```

</CodeTabs>

En Spring Boot, el contenedor hace este cableado por ti: anotas las implementaciones con `@Service` o `@Repository` y, si la clase tiene un solo constructor, Spring le inyecta los beans sin necesidad de `@Autowired`. Puntos que suman en la respuesta: prefiere **inyección por constructor** (las dependencias quedan explícitas y el objeto nunca existe a medio configurar) sobre la inyección por setter o por campo; un contenedor de DI es **opcional**, y en proyectos medianos armar el grafo a mano en un `main` es perfectamente válido; y el patrón opuesto, el *Service Locator* (pedir dependencias a un registro global desde dentro de la clase), esconde las dependencias y complica los tests. El tema de [patrones de aplicación](/patrones/patrones-aplicacion) tiene más detalle.

## Demeter, DRY, KISS, YAGNI y sus excesos

Estos cuatro principios aparecen como preguntas cortas ("¿qué es la Ley de Demeter?") o como argumento en una revisión de código. La diferencia entre una respuesta junior y una senior está en conocer **el exceso** de cada uno.

**Ley de Demeter** (o "principio del mínimo conocimiento"). Un método solo debería hablar con sus "amigos inmediatos": sus propios campos, sus parámetros y los objetos que crea. Nada de recorrer la estructura interna de otros.

<CodeTabs>

```java title="Java"
// Viola Demeter: esta clase conoce la forma interna de cuatro objetos
String codigo = pedido.getCliente().getDireccion().getPais().getCodigo();
// Mejor: pregúntale al pedido lo que necesitas
String pais = pedido.paisDeDestino();
```

```ts title="TypeScript"
// Viola Demeter: esta clase conoce la forma interna de cuatro objetos
const codigo = pedido.cliente.direccion.pais.codigo
// Mejor: pregúntale al pedido lo que necesitas
const pais = pedido.paisDeDestino()
```

</CodeTabs>

*Exceso:* llenar las clases de métodos que solo reenvían (`pedido.codigoPaisDelClienteDelPedido()`). Y no confundir con las APIs fluidas: `query.where(...).orderBy(...).limit(10)` encadena llamadas sobre el mismo tipo de objeto y no expone estructura interna.

**DRY** (*Don't Repeat Yourself*, de *The Pragmatic Programmer*). Cada pieza de **conocimiento** debe tener una representación única. No habla de líneas de texto parecidas, sino de reglas de negocio: si el IVA se calcula en tres lugares, el día que cambie vas a olvidar uno. *Exceso:* unificar dos fragmentos que se parecen por casualidad. Como dice Sandi Metz, la duplicación es mucho más barata que la abstracción equivocada. Si dos funciones se parecen pero cambian por motivos distintos, no son la misma.

**KISS** (*Keep It Simple*). La solución más simple que resuelve el problema real. *Exceso:* usarlo como excusa para no modelar nada ("un script de 2.000 líneas es simple").

**YAGNI** (*You Aren't Gonna Need It*). No construyas flexibilidad para un futuro imaginado. *Exceso:* ignorar decisiones caras de revertir. YAGNI aplica a funcionalidad especulativa; no te exime de pensar en el formato de los datos, la API pública o la seguridad, que son caros de cambiar después.

<Callout type="warn" title="SOLID contra YAGNI">

Hay una tensión real entre "abierto a extensión" y "no lo vas a necesitar", y es una excelente pregunta senior. La forma de resolverla: aplica SOLID **cuando aparece el dolor** (el segundo transportista, el test que no puedes escribir), no por anticipado. Con un solo caso, la función simple gana; con el segundo, extraer la interfaz es un refactor de minutos y lo haces con información real.

</Callout>

<Takeaways>

- Cada pilar tiene un para qué: **encapsular** protege invariantes (no es poner getters y setters), **abstraer** decide qué exponer, **heredar** especializa y **polimorfismo** permite agregar casos sin tocar a quien los usa.
- **Interfaz** es un contrato que cumplen tipos no relacionados; **clase abstracta** comparte estado y esqueleto. Conoce los matices de tu lenguaje: `default` en Java 8, interfaces estructurales en TypeScript, `Protocol` y `ABC` en Python.
- La herencia se rompe por la **clase base frágil** y por la **explosión combinatoria** cuando hay varios ejes. La composición deja variar cada eje por separado y en tiempo de ejecución.
- Para cada principio SOLID, ten una definición precisa, un ejemplo propio y su error típico. SRP es "un actor", la señal de Liskov es el `instanceof` y DIP no es lo mismo que inyección de dependencias.
- A "¿cómo aplicaste SOLID?" se responde con una historia: problema, decisión, resultado y dónde decidiste **no** aplicarlo.
- Demeter, DRY, KISS y YAGNI tienen excesos. Saber nombrarlos es lo que distingue una respuesta senior.

</Takeaways>
