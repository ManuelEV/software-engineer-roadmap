"Diseña un acortador de URLs como bit.ly." Es la pregunta de calentamiento más común de las entrevistas de system design, y por eso mismo es peligrosa: todo el mundo cree que la sabe. La versión ingenua se dibuja en dos minutos (una tabla `código → URL` y un servidor). La versión que aprueba una entrevista senior se gana en los detalles: cómo generas millones de códigos únicos sin un cuello de botella central, por qué la redirección es un problema de caché y no de base de datos, qué código HTTP devuelves y qué pierdes con cada opción.

Es un clásico porque el alcance funcional es mínimo y deja todo el tiempo para lo que importa: **generación de IDs**, **un patrón de lectura extremo** (cada link se crea una vez y se abre cientos de veces) y **trabajo asíncrono** para la analítica. Si dominas este caso, ya tienes las piezas de la mitad de los demás.

## Requisitos

Empieza siempre acotando. En la entrevista, dilo en voz alta y escribe la lista en la pizarra.

**Funcionales**

1. Dada una URL larga, el sistema devuelve una URL corta única (`sho.rt/aZ3x9Qk`).
2. Al abrir la URL corta, el usuario termina en la URL larga.
3. Opcional: alias personalizado (`sho.rt/black-friday`) y fecha de expiración.
4. Opcional: contar clics por link (analítica básica).

**No funcionales**

- **Latencia de redirección muy baja**: supongamos menos de 50 ms en p99 medido en el servidor. Cada milisegundo se suma a la carga de la página destino.
- **Disponibilidad alta en la lectura**: si las redirecciones fallan, se rompen millones de links publicados en todas partes. La escritura puede ser algo menos disponible.
- **Unicidad estricta**: dos URLs largas distintas nunca pueden compartir código.
- **Códigos no enumerables** (deseable): que no se pueda recorrer `aaaaaa`, `aaaaab`… y descubrir links privados.
- La analítica puede ser **eventualmente consistente** (un retraso de minutos es aceptable).

**Fuera de alcance** (dilo explícitamente): cuentas de usuario y facturación, edición del destino de un link ya creado, paneles de analítica detallados.

<Callout type="interview">

Pregunta antes de asumir: "¿Los links pueden editarse o borrarse?", "¿Necesitamos analítica en tiempo real?", "¿Los links son privados o públicos?". Cada respuesta cambia una decisión importante más adelante (301 vs 302, enumeración, consistencia).

## Estimaciones

Supongamos **100 millones de URLs nuevas al mes** y una relación lectura/escritura de **100 a 1**. Son supuestos razonables para un servicio grande; lo que importa es la aritmética.

| Magnitud | Cálculo | Resultado |
|---|---|---|
| Escrituras promedio | 100 M ÷ (30 × 86.400 s) | ~39 por segundo |
| Escrituras pico (×5) | 39 × 5 | ~200 por segundo |
| Lecturas promedio | 39 × 100 | ~3.900 por segundo |
| Lecturas pico (×5) | 3.900 × 5 | ~20.000 por segundo |
| Registros en 10 años | 100 M × 12 × 10 | 12.000 millones |
| Almacenamiento | 12.000 M × ~500 B | ~6 TB |

Tres conclusiones salen de esta tabla, y conviene decirlas:

1. **La escritura es trivial.** 200 escrituras por segundo las aguanta una sola base de datos modesta. El reto de escritura no es el volumen sino la **unicidad** del código.
2. **La lectura domina**, pero 20.000 por segundo tampoco es enorme si casi todo sale de memoria. El diseño de lectura es un diseño de caché.
3. **6 TB en diez años** ya no caben cómodos en un solo nodo con índices y réplicas. Planea particionar desde el principio, aunque empieces con pocos nodos.

**¿Cuántos caracteres necesita el código?** Con un alfabeto base62 (`0-9`, `a-z`, `A-Z`), cada carácter aporta log₂(62) ≈ 5,95 bits.

- 6 caracteres: 62⁶ ≈ **56.800 millones** de códigos. Alcanza para 12.000 millones de registros si los asignas sin desperdicio (con un contador).
- 7 caracteres: 62⁷ ≈ **3,5 billones**. Con 12.000 millones ocupados, el espacio está lleno al 0,34 %: si generas códigos al azar, solo uno de cada ~290 intentos choca.

**Caché.** Las lecturas siguen una ley de potencias: pocos links concentran casi todos los clics. Si mantienes en memoria los 50 millones de links más calientes a ~500 bytes cada uno, son unos 25 GB: cabe en un puñado de nodos de Redis con réplica.

## Entidades y API

Dos entidades bastan: **Link** (código, URL larga, dueño, fechas) y, si hay analítica, **Clic** (código, timestamp, país, referer, dispositivo).

```http
POST /v1/links
Authorization: Bearer <api-key>
Content-Type: application/json

{ "long_url": "https://tienda.ejemplo.com/ofertas?utm_source=mail",
  "custom_alias": "black-friday",      // opcional
  "expires_at": "2026-12-31T23:59:59Z" // opcional }

201 Created
{ "code": "black-friday", "short_url": "https://sho.rt/black-friday" }
```

```http
GET /aZ3x9Qk

302 Found
Location: https://tienda.ejemplo.com/ofertas?utm_source=mail
Cache-Control: private, max-age=90
```

```http
GET /v1/links/aZ3x9Qk/stats?from=2026-11-01&to=2026-11-19
Authorization: Bearer <api-key>

200 OK
{ "clicks": 18234, "unique_visitors_approx": 11020, "by_country": { "MX": 7012, "CO": 3110 } }
```

Detalles que suman puntos:

- **El `POST` está limitado por tasa** por API key (mira el caso del [rate limiter](/casos/rate-limiter)). Un acortador abierto es una herramienta perfecta para spammers.
- **Errores claros**: `409 Conflict` si el alias ya existe; `404` si el código no existe; `410 Gone` si expiró (así el cliente distingue "nunca existió" de "existió y caducó").
- **¿Deduplicar?** Si dos personas acortan la misma URL larga, ¿reciben el mismo código? Deduplicar globalmente ahorra poco espacio y filtra información (sabrías que alguien más acortó esa URL). Lo normal es deduplicar, si acaso, **por usuario**.

## Modelo de datos

El patrón de acceso dominante es una búsqueda puntual por clave: `código → URL larga`. Eso pide un almacén clave-valor o una tabla con clave primaria simple.

```sql
CREATE TABLE links (
  code        VARCHAR(16) PRIMARY KEY,   -- 7 chars generados o alias personalizado
  long_url    TEXT        NOT NULL,      -- hasta ~2 KB en la práctica
  owner_id    BIGINT,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  expires_at  TIMESTAMPTZ
);
CREATE INDEX links_owner ON links (owner_id, created_at DESC);  -- "mis links"
```

**¿Qué base de datos?** Hay dos respuestas defendibles:

- **Un almacén clave-valor distribuido** (DynamoDB, Cassandra, ScyllaDB). Particiona solo por la clave, escala horizontalmente sin esfuerzo y el `get` por clave es exactamente su punto fuerte. El índice secundario por dueño es menos cómodo, pero es un acceso raro.
- **Postgres particionado** (por hash del código). Más flexible para consultas administrativas y con transacciones para los alias; exige operar el [sharding](/system-design/replicacion-y-sharding) tú mismo.

Un detalle sutil: si tus códigos salen de un **contador secuencial** y la base particiona por **rango**, todos los códigos nuevos caen en la misma partición (un *hot spot* de escritura). Con particionado por **hash**, o con códigos que no son secuenciales, el problema desaparece.

## Profundizaciones

### 1. Generar el código: cuatro opciones

Aquí se decide la entrevista. Hay cuatro familias de soluciones y cada una tiene un costo distinto.

**Opción A: hash de la URL.** Calcula SHA-256 de la URL larga, toma los primeros 41 bits (2⁴¹ ≈ 2,2 billones, menos que 62⁷) y codifícalos en base62: caben en 7 caracteres. Ventaja: la misma URL siempre produce el mismo código, así que deduplicas gratis. Problema: **truncar un hash produce colisiones**. Tienes que leer antes de escribir para comprobar que el código está libre y, si choca, volver a hashear con una sal. Además, el código es determinista: cualquiera que conozca la URL puede calcular su link corto.

**Opción B: aleatorio con escritura condicional.** Genera 7 caracteres al azar con un generador criptográfico e inserta con una condición de "solo si no existe" (`INSERT … ON CONFLICT DO NOTHING` en Postgres, `attribute_not_exists(code)` en DynamoDB). Si choca, reintentas. Con el espacio al 0,34 % de ocupación, el reintento es rarísimo. Ventaja: cero coordinación y códigos imposibles de adivinar. Costo: la probabilidad de choque crece con la ocupación, y necesitas que la base soporte la escritura condicional.

**Opción C: contador + base62.** Un contador global nunca repite, así que el código es único por construcción y lo más corto posible. El problema evidente es que un contador central es un punto único de falla y de contención. La solución clásica es **asignar rangos**: cada servidor pide un bloque de 10.000 IDs al asignador (un `INCRBY` en Redis, una secuencia de base de datos o un nodo en ZooKeeper) y los consume localmente. Si un servidor muere, se pierden los IDs de su bloque: no importa, sobran.

**Opción D: servicio de generación de claves (KGS).** Un proceso genera por adelantado claves aleatorias únicas y las guarda en una tabla de "claves libres". Los servidores toman lotes y los marcan como usados. Es la opción B con el chequeo de colisiones hecho fuera de línea. Costo: otro servicio que operar, y cuidado con la concurrencia (dos servidores no pueden tomar la misma clave; usa `SELECT … FOR UPDATE SKIP LOCKED` o reparte rangos de la tabla por servidor).

Así se ve la opción C dentro de una instancia del servicio de escritura. El `synchronized` protege el bloque local entre hilos; la llamada al asignador ocurre una vez cada 10.000 links, así que mantener el lock durante esa llamada es aceptable. Si no lo fuera, se puede pedir el bloque siguiente en segundo plano antes de agotar el actual.

```java title="IdBlockAllocator.java"
/** Codifica un ID numérico en base62 (0-9, a-z, A-Z). */
final class Base62 {
    private static final char[] ALPHABET =
        "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ".toCharArray();

    static String encode(long id) {
        if (id == 0) return "0";
        StringBuilder sb = new StringBuilder();
        while (id > 0) {
            sb.append(ALPHABET[(int) (id % 62)]);
            id /= 62;
        }
        return sb.reverse().toString(); // los dígitos salen al revés
    }
}

/** Cada instancia pide bloques de IDs al asignador y los consume en memoria. */
final class IdBlockAllocator {
    /** Por ejemplo, INCRBY en Redis o una secuencia de la base: devuelve el total nuevo. */
    interface Allocator {
        long incrBy(long n);
    }

    private static final long BLOCK = 10_000;
    private final Allocator allocator;
    private long next = 0; // [next, end) es el bloque actual
    private long end = 0;

    IdBlockAllocator(Allocator allocator) {
        this.allocator = allocator;
    }

    synchronized String nextCode() {
        if (next == end) {               // una llamada de red cada 10.000 links
            end = allocator.incrBy(BLOCK);
            next = end - BLOCK;
        }
        return Base62.encode(next++);
    }
}
```

**¿Y si los códigos secuenciales son un problema?** Con un contador, `aZ3x9Qk` y `aZ3x9Ql` son links vecinos: un atacante puede recorrerlos y encontrar documentos compartidos "en privado". La solución es aplicar una **permutación biyectiva** al ID antes de codificarlo: por ejemplo, multiplicar por un número grande coprimo con 62⁷ y tomar el módulo, o una pequeña red de Feistel. La función sigue siendo uno a uno (no hay colisiones), pero IDs consecutivos producen códigos que parecen aleatorios.

### 2. ¿301 o 302? Una decisión de producto disfrazada de detalle técnico

Ambos códigos redirigen. La diferencia está en el **caché del navegador**:

- **301 Moved Permanently** es cacheable por defecto según HTTP (RFC 9110). El navegador puede recordar la redirección y, la próxima vez, ir directo al destino sin pasar por tu servidor. Ahorras carga y latencia.
- **302 Found** (o **307**, que además conserva el método) no se cachea salvo que lo indiques con headers. Cada clic pasa por tu servidor.

¿Qué pierdes con 301? **Visibilidad y control.** Los clics repetidos del mismo navegador no llegan a ti, así que la analítica subestima. Y si descubres que un link apunta a phishing, no puedes desactivarlo para quien ya lo tiene en caché. Tampoco puedes hacer expirar el link de forma confiable.

La respuesta madura: **302 con un `Cache-Control` corto** (por ejemplo, `private, max-age=90`). Tienes control y analítica, y aun así absorbes los dobles clics y recargas. Si el producto no tiene analítica ni moderación (un acortador interno, por ejemplo), un 301 es razonable.

### 3. La ruta de lectura es un problema de caché

Con 20.000 lecturas por segundo en pico y un hot set de 25 GB, el diseño es *cache-aside* clásico (repásalo en [caching](/system-design/caching)):

1. Busca en Redis. Si está, responde.
2. Si no, lee de la base, guarda en Redis con TTL (por ejemplo, 24 h con una variación aleatoria para que no expiren todos a la vez) y responde.

Tres refinamientos separan una respuesta buena de una excelente:

- **Caché negativo.** Guarda también los códigos inexistentes (con un TTL corto). Sin esto, un bot que prueba códigos al azar convierte cada intento en una lectura a la base.
- **Claves calientes.** Un link viral (un tuit de una celebridad) puede recibir decenas de miles de clics por segundo en una sola clave de Redis, que vive en un solo nodo. Mitigaciones: un caché **en el proceso** (L1) de cada instancia con TTL de segundos, o réplicas de lectura de Redis. Con 200 instancias y un L1 de 5 segundos, Redis ve como mucho 40 lecturas por segundo de esa clave.
- **El borde.** Puedes resolver redirecciones en el CDN o en funciones *edge* con un almacén replicado globalmente. La latencia baja a lo que tarda el PoP más cercano. El costo: el origen deja de ver los clics, así que la analítica tiene que salir de los logs del borde.

### 4. Analítica sin frenar la redirección

La regla: **la redirección nunca espera a la analítica**. El servicio emite un evento (`code`, timestamp, IP truncada, user-agent, referer) a un buffer local que se vacía hacia Kafka, y responde de inmediato. Si Kafka tiene un mal día, pierdes algunos eventos; no pierdes redirecciones.

Del lado del consumo, un job de streaming (Flink, Kafka Streams) agrega por `(code, minuto)` y escribe en una base analítica columnar (ClickHouse, Druid). Para visitantes únicos no guardes conjuntos de IPs: usa **HyperLogLog**, que en Redis estima cardinalidades con un error estándar de 0,81 % usando como máximo 12 KB por clave, sin importar si son mil o mil millones de visitantes.

<Details summary="Profundizar: alias personalizados y expiración">

**Alias.** Viven en el mismo espacio de claves que los códigos generados, así que un alias puede chocar con un código futuro. Dos salidas: reservar un formato distinto (los generados tienen exactamente 7 caracteres; los alias, otra longitud o un guion obligatorio) o insertar siempre con escritura condicional y devolver `409` al perdedor. Mantén una lista de palabras reservadas (`api`, `login`, `admin`).

**Expiración.** Comprueba `expires_at` al leer (responde `410`) y limpia en lote con un job nocturno. **No recicles códigos expirados**: los links viejos siguen impresos en carteles, PDFs y correos, y reciclarlos mandaría a esas personas a un destino que nadie eligió.

</Details>

## Cuellos de botella y trade-offs

| Riesgo | Síntoma | Mitigación |
|---|---|---|
| Asignador de IDs central | Latencia o caída al crear links | Bloques de IDs por instancia; asignador replicado (Redis con réplica, ZooKeeper, secuencia en una base con failover) |
| Clave caliente | Un nodo de Redis saturado por un link viral | Caché L1 en proceso, réplicas de lectura, resolución en el borde |
| Escaneo de códigos | Picos de lecturas a la base con 404 | Caché negativo, rate limiting por IP, códigos no secuenciales |
| Abuso (phishing, malware) | Reportes, dominio bloqueado por navegadores | Escaneo asíncrono contra listas como Google Safe Browsing, 302 para poder desactivar, límites de creación |
| Multi-región | Latencia alta lejos de la región principal | Lecturas desde réplicas regionales; cada región con su propio rango de IDs para que nunca choquen |

El trade-off de fondo de todo el caso: **mover trabajo fuera de la ruta crítica**. Generar IDs en bloques, agregar clics de forma asíncrona y limpiar expirados en lote son la misma idea aplicada tres veces.

<Callout type="interview" title="Por nivel">

**Mid-level.** Requisitos claros, API correcta, estimaciones razonables, base62 sobre un contador o aleatorio con chequeo, una caché delante de la base. Que el diseño funcione de punta a punta.

**Senior.** Comparar las opciones de generación con sus costos (colisiones, coordinación, enumeración), calcular el espacio de códigos, separar lectura y escritura, justificar 301 vs 302, caché negativo y claves calientes, analítica asíncrona. Detectar los cuellos de botella sin que te los señalen.

**Staff.** Llevar la conversación hacia la operación y el producto: multi-región y asignación de rangos por región, abuso y moderación, qué pasa cuando el asignador cae, costo de la infraestructura, privacidad de los datos de clics (IPs, retención), y cómo evolucionaría el sistema si mañana piden editar destinos o links con contraseña.

<Takeaways>

- La escritura es poca; el reto es la **unicidad sin coordinación**. Bloques de IDs por instancia o códigos aleatorios con escritura condicional resuelven lo mismo con costos distintos.
- Haz la cuenta del espacio: 62⁶ ≈ 56.800 millones, 62⁷ ≈ 3,5 billones. Con códigos aleatorios importa la **ocupación**, no solo el total.
- La ruta de lectura es un diseño de **caché**: cache-aside, caché negativo, L1 para claves calientes y, si hace falta, el borde.
- **301 ahorra carga, 302 conserva el control.** Analítica, moderación y expiración piden 302 con un `max-age` corto.
- La analítica va **fuera de la ruta crítica**: evento asíncrono, agregación en streaming, HyperLogLog para únicos.
- Los códigos secuenciales son enumerables: aplica una permutación biyectiva si los links pueden ser privados.

</Takeaways>
