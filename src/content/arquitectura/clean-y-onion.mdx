Entre 2005 y 2012 aparecieron varias arquitecturas con nombres distintos y dibujos distintos: hexagonal (Cockburn, 2005), Onion (Jeffrey Palermo, 2008), Clean Architecture (Robert C. Martin, 2012). En entrevistas y en equipos se discuten como si fueran rivales. No lo son. Son variaciones de **una sola idea**: poner el dominio en el centro y hacer que todas las dependencias de código apunten hacia él.

Este tema explica esa idea con el vocabulario de Clean Architecture, que es el más detallado; muestra qué agrega Onion; compara las cuatro (incluidas las capas clásicas) en una tabla, y termina con la parte que más falta en los tutoriales: cuándo todo esto es exceso de ingeniería.

## La regla de dependencia

En 2012, Robert C. Martin (*Uncle Bob*) publicó en su blog *The Clean Architecture*. El artículo dice explícitamente que intenta unificar varias arquitecturas previas (hexagonal, Onion, *Screaming Architecture*, DCI y BCE) y que todas comparten un objetivo: separar intereses dividiendo el software en capas, con al menos una para las reglas de negocio y otra para las interfaces.

El dibujo son cuatro círculos concéntricos, de adentro hacia afuera:

- **Entidades** (*Entities*): reglas de negocio de la empresa, las que existirían aunque no hubiera software. "Un pedido no puede tener total negativo".
- **Casos de uso** (*Use Cases*): reglas de negocio de **esta** aplicación. "Al confirmar un pedido, reservar stock y cobrar". Orquestan entidades.
- **Adaptadores de interfaz** (*Interface Adapters*): controladores, *presenters*, *gateways*, repositorios. Convierten datos entre el formato cómodo para los casos de uso y el formato cómodo para el exterior.
- **Frameworks y drivers**: el framework web, el driver de la base, la UI. Pegamento, idealmente poco código.

Y una sola regla, que es lo único que tienes que recordar: **las dependencias de código fuente solo pueden apuntar hacia adentro**<Sidenote>En el original: "source code dependencies can only point inwards". Martin aclara que cuatro círculos es un esquema: puedes tener más, pero la regla siempre aplica.</Sidenote>. Nada en un círculo interior puede conocer el nombre de algo en un círculo exterior: ni una clase, ni una función, ni un tipo.

### Qué cruza las fronteras

La regla también aplica a los datos. Martin propone que por las fronteras crucen **estructuras simples**: DTOs, argumentos de función, objetos planos. No entidades y, sobre todo, no filas de la base de datos ni objetos del framework. Si tu caso de uso recibe un `Request` de Express o devuelve un `Row` de `pg`, el círculo interior acaba de conocer un nombre del exterior.

## Flujo de control vs dirección de dependencias

Aquí está el truco que confunde a todos la primera vez. En ejecución, el caso de uso **llama** a la base de datos y **produce** una respuesta para la UI: el flujo de control va de adentro hacia afuera. ¿Cómo puede ser que la dependencia de código apunte hacia adentro?

Con el **principio de inversión de dependencias**. El caso de uso define una interfaz (un puerto de salida) y la usa; el adaptador de afuera la implementa. En ejecución el control va hacia afuera; en el código, el adaptador importa la interfaz de adentro.

## Casos de uso como ciudadanos de primera clase

Lo que Clean Architecture enfatiza más que hexagonal es el círculo de **casos de uso**. Cada caso de uso es una clase (o función) con nombre de negocio, un modelo de entrada y un modelo de salida. Martin lo conecta con otra idea suya, *Screaming Architecture*: si miras las carpetas de un sistema de pedidos, deberían "gritar" pedidos, pagos y envíos, no Spring, Rails o Express.

```ts title="src/orders/use-cases/confirm-order.ts"
import type { OrderGateway } from './ports'
import { DomainError } from '../entities/order'

// Modelos de entrada y salida: estructuras simples, sin tipos del framework.
export interface ConfirmOrderInput {
  orderId: string
  confirmedBy: string
}
export interface ConfirmOrderOutput {
  orderId: string
  status: 'CONFIRMED'
  totalCents: number
}

export class ConfirmOrder {
  constructor(
    private readonly orders: OrderGateway,
    private readonly clock: () => Date,
  ) {}

  async execute(input: ConfirmOrderInput): Promise<ConfirmOrderOutput> {
    const order = await this.orders.byId(input.orderId)
    if (!order) throw new DomainError('Pedido inexistente')

    order.confirm(input.confirmedBy, this.clock()) // la regla vive en la entidad
    await this.orders.save(order)

    return { orderId: order.id, status: 'CONFIRMED', totalCents: order.totalCents() }
  }
}
```

Fíjate en el `clock`. Hasta la hora actual es una dependencia del exterior: si el caso de uso llamara a `new Date()` directamente, no podrías probar "un pedido no se puede confirmar después de 30 minutos" sin esperar 30 minutos.

### ¿Presenter o valor de retorno?

El diagrama original de Martin usa un **presenter**: el caso de uso no devuelve nada, sino que llama a un puerto de salida. Esto tiene sentido cuando el mismo caso de uso alimenta varias salidas (pantalla, PDF, notificación) o en UIs con estado. En una API web típica, **devolver un modelo de salida** y dejar que el controlador lo serialice es más simple y respeta la regla de dependencia igual de bien: el modelo de salida vive en el círculo de casos de uso y el controlador lo importa. No pagues la indirección del presenter si no tienes varias salidas.

## Onion Architecture

Jeffrey Palermo publicó *The Onion Architecture* en una serie de tres posts en 2008. Su crítica a las capas clásicas era directa: el gran problema es el **acoplamiento** que crean. La UI depende de la lógica, que depende del acceso a datos, que depende de la infraestructura; y como las dependencias son transitivas, todo termina dependiendo de la tecnología de acceso a datos, que cambia cada pocos años.

Su propuesta, en sus propias palabras, se resume en cuatro principios:

1. La aplicación se construye alrededor de un **modelo de objetos independiente**.
2. Las capas internas **definen interfaces**; las capas externas las **implementan**.
3. La dirección del acoplamiento es **hacia el centro**.
4. Todo el código del núcleo de la aplicación puede **compilarse y ejecutarse separado de la infraestructura**.

Las capas que dibuja Palermo son: el **modelo de dominio** en el centro; alrededor, las **interfaces de repositorios** y los **servicios de dominio**; luego los **servicios de aplicación**; y en el borde exterior, juntos, **UI, infraestructura y tests**. Que los tests estén en el mismo anillo que la UI no es casual: igual que en hexagonal, un test es solo otro cliente del núcleo.

La frase que mejor resume Onion es suya: la base de datos **no es el centro**, es externa. Si vienes de diseñar empezando por el esquema de tablas, ese es el cambio de mentalidad.

<Callout type="idea" title="Mismo principio, distinto énfasis">

Hexagonal enfatiza la **simetría** adentro/afuera y los puertos por propósito. Onion enfatiza las **capas concéntricas dentro del núcleo** (dominio, servicios de dominio, aplicación). Clean enfatiza los **casos de uso** como unidad y las reglas sobre qué datos cruzan cada frontera. Mark Seemann lo resumió en un post de 2013 con un título que lo dice todo: *Layers, Onions, Ports, Adapters: it's all the same*.

</Callout>

## Comparación lado a lado

| | Capas clásicas | Hexagonal | Onion | Clean |
| --- | --- | --- | --- | --- |
| Autor y año | Tradición (popularizada en los 90) | Alistair Cockburn, 2005 | Jeffrey Palermo, 2008 | Robert C. Martin, 2012 (libro en 2017) |
| Qué está en el centro | Nada: la base está abajo | La aplicación (dominio + casos de uso) | El modelo de dominio | Las entidades |
| Dirección de dependencias | Hacia abajo, hacia la persistencia | Hacia adentro, desde ambos lados | Hacia el centro | Hacia adentro (la regla de dependencia) |
| Estructura interna del núcleo | No aplica | No la prescribe | Dominio, servicios de dominio, servicios de aplicación | Entidades y casos de uso |
| Vocabulario clave | Presentación, negocio, persistencia | Puertos, adaptadores, conductor/conducido | Interfaces internas, implementaciones externas | Interactor, puertos de entrada/salida, presenter, gateway |
| ¿Se prueba el núcleo sin infraestructura? | Difícil | Sí | Sí | Sí |
| Riesgo típico | Dominio anémico, todo depende de la base | Puertos que copian la tecnología | Demasiadas capas internas | Ceremonia: interactor + presenter + DTOs para un CRUD |

Lo que las tres modernas comparten es más importante que lo que las separa:

- El **dominio no conoce la infraestructura**.
- Las **interfaces las define quien las usa** (el núcleo), no quien las implementa.
- La infraestructura es un **detalle reemplazable**, incluida la base de datos.
- El núcleo se puede **probar sin levantar nada**.

En una entrevista, si te preguntan la diferencia, da la tabla en una frase y después di lo importante: en la práctica casi nadie implementa ninguna de las tres "pura", y la mayoría de los equipos usa una mezcla con el vocabulario de hexagonal (puertos y adaptadores) y la estructura de casos de uso de Clean.

## Cuándo es exceso de ingeniería

La crítica más común a Clean Architecture no es al principio sino a cómo se aplica. Hay plantillas populares que, para un CRUD, generan cinco proyectos, un interactor, un presenter, un *request model*, un *response model*, un *view model*, un *gateway* y un *mapper* por cada endpoint. Eso no es Clean Architecture: es aplicar un dibujo sin preguntarse qué problema resuelve.

Tres señales de que te pasaste:

- **Los casos de uso solo delegan.** `GetOrderUseCase.execute(id)` llama a `repo.findById(id)` y devuelve el resultado. Para lecturas simples, deja que el adaptador lea directamente con una consulta optimizada (es lo que CQRS formaliza).
- **Los *mappers* superan a la lógica.** Si para agregar un campo tocas ocho archivos de mapeo y ninguno de reglas, el costo de la separación es mayor que su beneficio.
- **Las entidades son anémicas.** Si las "entidades" del círculo central solo tienen propiedades, toda la complejidad está en los casos de uso y el círculo interior no está protegiendo nada.

Una alternativa que ganó adopción es la **Vertical Slice Architecture** que describe Jimmy Bogard: organizar por funcionalidad (cada *slice* es una petición con todo lo que necesita, de punta a punta) y aplicar abstracciones solo dentro de las slices que las necesitan. Combina bien con lo anterior: slices simples para lecturas y CRUD, y un núcleo con dominio rico y puertos para las partes del negocio con reglas de verdad.

<Callout type="tip" title="Regla práctica">

Aplica la regla de dependencia **siempre** (el dominio nunca importa infraestructura; cuesta casi nada). Aplica la **ceremonia completa** (interactor, presenter, modelos separados por capa) solo donde el dominio es complejo y cambia seguido. La regla es barata; la ceremonia no.

</Callout>

<Takeaways>

- Hexagonal, Onion y Clean son la misma idea: el dominio en el centro y todas las dependencias de código apuntando hacia él.
- La regla de dependencia: nada interior conoce nombres exteriores, y por las fronteras cruzan estructuras simples, no entidades ni objetos del framework.
- El flujo de control puede ir hacia afuera mientras la dependencia apunta hacia adentro: el núcleo define la interfaz y el adaptador la implementa.
- Clean aporta los casos de uso como unidad con modelos de entrada y salida; Onion aporta las capas internas del núcleo y la frase "la base de datos no es el centro".
- Devolver un modelo de salida suele bastar; el presenter paga cuando hay varias salidas para el mismo caso de uso.
- La regla es barata y siempre vale; la ceremonia completa solo donde hay reglas de negocio complejas. Para lecturas y CRUD, slices o consultas directas.

</Takeaways>
